# Лабораторная работа №1

## Что есть в проекте

| Папка | Что это | Задание |
|---|---|---|
| `WS01-01/` | сервис, хранит стек **на сервере** (в сессии) | 1 |
| `WS01-02/` | такой же сервис, но стек хранится **у клиента** (в cookie) | 3 |
| `Gateway/` | прокси, который принимает запросы и раздаёт их двум копиям сервиса | 2, 4 |
| `docker-compose.yml` | поднимает всё сразу в Docker | — |
| `http/` | готовые запросы для REST Client | — |

## Как работает сервис (WS01-01 и WS01-02)

У каждого клиента есть два значения:

- `RESULT` — число, сначала `0`;
- стек чисел, сначала пустой.

Все запросы идут на один адрес `/stack`:

| Запрос | Что делает |
|---|---|
| `GET /stack` | возвращает `{"RESULT": RESULT + верхний элемент стека}` |
| `POST /stack` с телом `{"RESULT": 10}` | записывает `RESULT = 10` |
| `PUT /stack?ADD=5` | кладёт `5` на вершину стека |
| `DELETE /stack` | снимает верхний элемент; если стек пуст — ошибка `409` |

Пример:

```
POST {"RESULT":10}  -> 10   (стек пуст)
PUT  ?ADD=5         -> 15   (10 + 5)
PUT  ?ADD=7         -> 17   (10 + 7)
DELETE              -> 15   (7 снято, наверху 5)
DELETE              -> 10   (стек пуст)
```

В каждом ответе есть заголовок `X-Instance` — имя контейнера, который ответил. По нему видно работу балансировки.

### Разница между WS01-01 и WS01-02

**WS01-01 — данные на сервере.**
При первом запросе сервер выдаёт клиенту cookie `.WS01-01.Session` — это просто номер сессии. Сами `RESULT` и стек лежат в памяти этого контейнера. Клиент присылает номер, а сервер по нему находит его данные.
→ Другой контейнер про этого клиента ничего не знает.

**WS01-02 — данные у клиента.**
Сервер ничего не хранит. После каждого запроса он отправляет клиенту cookie `RESULT=10` и `STACK=5.7` (стек через точку). Клиент присылает их обратно, и сервер считает ответ по ним.
→ Любой контейнер может обслужить любого клиента.

## Как работает Gateway (задания 2 и 4)

Gateway — это отдельное ASP.NET Core-приложение на библиотеке YARP. Он стоит перед двумя одинаковыми контейнерами сервиса и пересылает им запросы. Один и тот же проект запускается в двух режимах:

**Sticky Session (задание 2, перед двумя WS01-01).**
На первом запросе gateway выбирает контейнер A или B и выдаёт клиенту cookie `.WS01.Affinity` с этим выбором. Дальше все запросы клиента идут **в тот же контейнер**.
Это нужно, потому что сессия WS01-01 лежит только в одном контейнере.

**Round Robin (задание 4, перед двумя WS01-02).**
Запросы идут по очереди: A, B, A, B…
Это работает, потому что у WS01-02 всё состояние приходит в cookie, и контейнеру неважно, кто обрабатывал прошлый запрос.

Режим выбирается файлом настроек: `appsettings.Sticky.json` или `appsettings.RoundRobin.json`.

## Схема

```
Задание 1:  клиент ──► :5001 WS01-01

Задание 2:  клиент ──► :5002 Gateway (Sticky) ──► ws01-01-a
                                              └─► ws01-01-b

Задание 3:  клиент ──► :5003 WS01-02

Задание 4:  клиент ──► :5004 Gateway (Round Robin) ──► ws01-02-a
                                                   └─► ws01-02-b
```

## Запуск

Нужен запущенный Docker Desktop. Из папки `lab1` выполните:

```bash
docker compose up -d --build     # запустить всё
docker compose down              # остановить
```

Каждое приложение собирается в **один исполняемый файл** под Linux, внутри которого уже есть .NET (self-contained / single-file). Поэтому контейнер работает без установленного .NET.

## Демонстрация

1. Установите в VS Code расширение **REST Client** (`humao.rest-client`).
2. Перед демонстрацией сбросьте cookie, которые сохранил REST Client: выполните в терминале `echo '{}' > ~/.rest-client/cookie.json`, затем **Cmd+Shift+P → `Developer: Reload Window`**. Иначе REST Client отправит cookie от прошлого прогона: вы не увидите `Set-Cookie` на первом запросе, а в стеке останутся старые значения.
3. Откройте файл из папки `http/` и нажимайте **Send Request** над запросами сверху вниз.
4. Справа откроется ответ. В нём смотрите на тело (`RESULT`) и заголовки `X-Instance` и `Set-Cookie`.

| Файл | Что должно получиться |
|---|---|
| `task1-ws01-01.http` | `RESULT` меняется как в примере выше; последний запрос (новый клиент) получает `0` |
| `task2-sticky.http` | все запросы клиента обрабатывает один и тот же `X-Instance`; новые клиенты (последний запрос, повторите его) попадают то на `a`, то на `b` |
| `task3-ws01-02.http` | то же, что в задании 1, но в ответах видны `Set-Cookie: RESULT=...`, `STACK=...`; последний запрос сам передаёт cookie и получает `4` |
| `task4-roundrobin.http` | `X-Instance` меняется на каждом запросе, а `RESULT` считается правильно |

Пояснения к `.http`-файлам:

- REST Client запоминает cookie, как браузер. Комментарий `# @no-cookie-jar` отправляет запрос без cookie, то есть от лица нового клиента.
- В файлах используются два адреса, `localhost` и `127.0.0.1`. REST Client хранит cookie по адресу без учёта порта, и так cookie одного задания не попадают в другое.
