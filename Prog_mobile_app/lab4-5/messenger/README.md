5. `BlocListener`: [post_form_screen.dart:41-45](lib/screens/post_form_screen.dart#L41-L45). После сохранения закрывает форму (навигация), при ошибке показывает `SnackBar`.
6. `context.read<HiveBloc>().add(...)`: [hive_screen.dart:18](lib/screens/hive_screen.dart#L18), [hive_screen.dart:44](lib/screens/hive_screen.dart#L44), [hive_screen.dart:49](lib/screens/hive_screen.dart#L49), [hive_screen.dart:88](lib/screens/hive_screen.dart#L88), [post_form_screen.dart:36](lib/screens/post_form_screen.dart#L36)

**Как работает:**
- Событие — это «что произошло», например `SelectUser('Anna')`. Состояние — это «что показать»: статус, пользователь, фильтр, лайки, ключи постов. И то и другое неизменяемо. Чтобы что-то поменять, BLoC создаёт новый объект через `copyWith`. `Equatable` сравнивает объекты по полям, поэтому одинаковое состояние не перерисовывает экран повторно.
- `MultiBlocProvider` стоит над `MaterialApp`, поэтому один `HiveBloc` виден со всех экранов: из ленты, из `HiveScreen` и из формы.
- `BlocBuilder` перерисовывает свой кусок UI на каждое новое состояние. На `HiveScreen` это весь экран, в ленте — только одна строка текста. Ленту и `HiveScreen` открывают как разные маршруты, но показывают они один и тот же BLoC: лайкнули пост в Hive, вернулись, а в ленте уже `Admin ♥ 1`.
- `BlocListener` ничего не рисует. Он выполняет действие один раз на смену состояния: `listenWhen` срабатывает, когда операция закончилась (было `loading`). Успех закрывает форму через `Navigator.pop`, ошибка показывает снекбар. Такие действия нельзя делать в `BlocBuilder`: `build` может вызываться много раз.
- Кнопки получают BLoC через `read` и вызывают `add(event)`. Им нужно только отправить событие, подписка не нужна, поэтому кнопка сама не перерисовывается.

## Ответы на вопросы

**1. Что такое BLoC и из каких компонентов он состоит?**
BLoC (Business Logic Component) — паттерн, который отделяет логику от UI. UI отправляет **события** (Event) — «что произошло». **Bloc** принимает их, выполняет логику и выдаёт **состояния** (State) — «что показать». События и состояния передаются через **потоки** (Stream): на вход идёт поток событий, на выход — поток состояний, а UI подписан на выходной поток.

**2. На каком механизме потоков основан BLoC и как это даёт реактивность?**
На `Stream` из Dart (внутри — `StreamController.broadcast`). Каждый `emit` кладёт новое состояние в поток. Все подписчики (`BlocBuilder`, `BlocListener`) получают его и обновляются сами, без ручного вызова «перерисуй». UI просто реагирует на поток состояний.

**3. Как `BlocBuilder` узнаёт об изменении состояния и чем он отличается от `StreamBuilder`?**
Он находит BLoC в дереве через `BlocProvider` и подписывается на его `stream`. На каждое новое состояние вызывается `builder`. В отличие от `StreamBuilder`:
- сразу есть текущее состояние (`bloc.state`), не нужно проверять `snapshot.hasData` или `ConnectionState`;
- есть `buildWhen`, чтобы перерисовываться не на каждое изменение;
- не нужно вручную передавать поток.

Одинаковые состояния (по `==`) BLoC не выдаёт вообще.

**4. Чем `BlocBuilder` отличается от `BlocListener`?**
`BlocBuilder` строит UI: его `builder` может вызываться много раз и должен только возвращать виджеты. `BlocListener` ничего не рисует. Он вызывает `listener` один раз на каждое новое состояние, поэтому подходит для побочных действий: навигации, снекбаров, диалогов. Если нужно и то и другое, есть `BlocConsumer`.

**5. Что такое `BlocProvider` и как он делает BLoC доступным потомкам?**
Это виджет на основе `provider`/`InheritedWidget`. Он создаёт BLoC в `create:`, хранит его и закрывает (`close()`) при удалении из дерева. Любой потомок может найти его вверх по дереву через `context.read<T>()`, `BlocBuilder` или `BlocListener`. `BlocProvider.value` отдаёт уже созданный BLoC и не закрывает его.

**6. Чем `MultiBlocProvider` отличается от вложенных `BlocProvider`?**
По работе ничем: `MultiBlocProvider` и превращается во вложенные провайдеры. Он нужен для читаемости: несколько BLoC объявляются плоским списком, а не «лесенкой» из вложенных `child:`.

**7. Где инициализировать BLoC и что будет, если создать его в `build()`?**
В `create:` у `BlocProvider`, который стоит выше всех виджетов, использующих этот BLoC. Если BLoC нужен нескольким экранам, провайдер ставят над `MaterialApp`. Если создать BLoC в `build()`, при каждой перерисовке появится новый экземпляр. Состояние будет сбрасываться, подписчики будут терять данные, а старые BLoC никто не закроет (утечки потоков).

**8. Как получить BLoC из виджета? Разница между `context.read<T>()` и `context.watch<T>()`?**
Через `context.read<HiveBloc>()`, `BlocProvider.of<HiveBloc>(context)` или `BlocBuilder`/`BlocListener`. `read` просто возвращает экземпляр без подписки и нужен в обработчиках нажатий, чтобы вызвать `add`. `watch` возвращает экземпляр и подписывает виджет: при каждом новом состоянии перестраивается весь `build`. Обычно вместо `watch` используют `BlocBuilder`, чтобы перерисовывать только нужный кусок.

**9. Как отправить событие и как это отразится на подписчиках?**
`context.read<HiveBloc>().add(SelectUser('Anna'))`. BLoC находит обработчик `on<SelectUser>`, тот вызывает `emit(новоеСостояние)`. Новое состояние уходит в поток, и все `BlocBuilder` перестраиваются, а `BlocListener` выполняют свой `listener`. Если новое состояние равно старому, ничего не произойдёт.

**10. Зачем Equatable или freezed для State и Event?**
По умолчанию Dart сравнивает объекты по ссылке: два одинаковых `HiveState` считаются разными. `Equatable` (или `freezed`) сравнивает по полям. Благодаря этому BLoC не выдаёт состояние, равное текущему, и UI не перерисовывается впустую. Так же проще писать тесты: `expect(state, HiveState(...))`. `freezed` дополнительно генерирует `copyWith`, `toString` и иммутабельность.

**11. Что такое `BlocObserver` и зачем он?**
Глобальный наблюдатель за всеми BLoC приложения. Он задаётся через `Bloc.observer = MyObserver()` и получает колбэки `onEvent`, `onChange`, `onTransition` и `onError`. В них удобно логировать каждое событие и переход «было → стало», ловить ошибки в одном месте и при отладке видеть, какое событие привело к неверному состоянию.

**12. Чем `Bloc` отличается от `Cubit`?**
`Cubit` проще: состояние меняется прямым вызовом метода `cubit.increment()` → `emit`, событий нет. `Bloc` принимает события через `add`, поэтому:
- видно не только новое состояние, но и причину (`onTransition`);
- можно управлять обработкой событий: `debounce`, отмена предыдущего запроса, очередь через `transformer`;
- всю историю удобно логировать.

`Cubit` хорош для простого состояния: переключатель, счётчик, форма. `Bloc` — для сложной асинхронной логики: поиск с `debounce`, цепочки запросов, когда важна трассировка событий.

**13. Как организовать loading / success / error через состояния?**
Добавить в состояние статус (enum или отдельные классы состояний). В обработчике сначала `emit(loading)`, затем `await` работы в `try`. Успех — `emit(success с данными)`, исключение в `catch` — `emit(error с текстом)`. UI в `BlocBuilder` по статусу показывает спиннер, данные или сообщение, а `BlocListener` реагирует на ошибку снекбаром. Так сделано в этой лабе (задание 5).

**14. Плюсы BLoC по сравнению с Provider и когда BLoC избыточен?**
Плюсы:
- чёткое разделение UI и логики;
- все изменения проходят через события, поэтому их легко отследить и залогировать (`BlocObserver`);
- состояния неизменяемы, нет случайных правок «мимо» `notifyListeners`;
- удобно тестировать: подал событие, проверил состояния;
- есть готовые инструменты для асинхронщины: `transformer`, `BlocListener`.

Минусы: много шаблонного кода (классы событий и состояний, `copyWith`). Для маленького приложения, простой формы или пары флагов BLoC избыточен: хватит `setState`, Provider или `Cubit`.
