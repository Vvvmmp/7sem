# Синхронизация потоков и времени (ЛР №3)

Продолжение [CONCURRENCY.md](CONCURRENCY.md) (ЛР №2). Там задокументирован и
воспроизведён Race Condition; здесь он устраняется, и добавляется
синхронизация времени клиента и сервера.

## Часть 1. Синхронизация доступа к общему ресурсу

### 1. Общий ресурс и место гонки (повтор анализа из ЛР №2)

Общий ресурс — `Seat.Status` (см. [CONCURRENCY.md, п.4](CONCURRENCY.md)).
Проблемное место — [`TicketSalesService.ReserveSeat`](src/TicketSales.Server/Domain/Services/TicketSalesService.cs):

1. **Чтение** — `seat.Status` читается в `if (seat.Status != SeatStatus.Free)`.
2. **Проверка** — сравнение с `SeatStatus.Free`.
3. **Изменение состояния** — `seat.Status = SeatStatus.Reserved; _seatRepository.Update(seat);`.
4. Между чтением/проверкой (1-2) и записью (3) не было никакой блокировки —
   поэтому второй поток, попавший в этот промежуток, тоже видел `Free` и тоже
   резервировал то же место (TOCTOU).

### 2. Критическая секция

Атомарной (неделимой относительно других клиентов) должна быть последовательность
"проверить `Free` → записать `Reserved` → создать `Ticket`" — именно она работает
с общим состоянием. Поиск/создание `Customer` (другой ресурс, `ICustomerRepository`)
в критическую секцию не входит и выполняется до входа в неё — это отвечает
Требованию 4 ("не помещать под блокировку весь метод").

```csharp
// src/TicketSales.Server/Domain/Services/TicketSalesService.cs, ReserveSeat
var customer = _customerRepository.FindByEmail(request.CustomerEmail); // вне lock
...

lock (_seatLock)
{
    if (seat.Status != SeatStatus.Free)
    {
        throw new ValidationException("Место уже занято");
    }

    seat.Status = SeatStatus.Reserved;
    _seatRepository.Update(seat);
    ticket = _ticketRepository.Add(new Ticket { ... });
}
```

Если бы проверка стояла вне `lock` (антипаттерн из Требования 6:
`check(); lock { update(); }`), два потока могли бы пройти проверку `Free`
одновременно и оба войти в `lock` по очереди, каждый уже "зная", что место
свободно, — и оба бы его записали. Поэтому проверка и запись обязаны быть
внутри одного и того же `lock`.

Тот же `_seatLock`-объект используется и в `BuyTicket`/`CancelTicket`
(тоже пишут в `Seat.Status`), чтобы бронирование/покупка/отмена одного места
не могли перекрыться друг с другом.

### 4. Требование 9 — SemaphoreSlim вместо lock

Второй проект: [`src/TicketSales.SemaphoreDemo`](src/TicketSales.SemaphoreDemo),
использующий [`TicketSalesServiceSemaphore`](src/TicketSales.Server/Domain/Services/TicketSalesServiceSemaphore.cs) —
копию сервиса, где `lock (_seatLock) { ... }` заменён на:

```csharp
await _seatSemaphore.WaitAsync();
try { /* тот же код критической секции */ }
finally { _seatSemaphore.Release(); }
```

где `_seatSemaphore = new SemaphoreSlim(1, 1)`.

```bash
dotnet run --project src/TicketSales.SemaphoreDemo
```

```
[21:52:58.504] [Thread 8]  ReserveSeat: seat=1 ACQUIRED -> Reserved -> FAIL -> RELEASE
[21:52:58.504] [Thread 15] ReserveSeat: seat=1 ACQUIRED -> Reserved -> FAIL -> RELEASE
[21:52:58.504] [Thread 13] ReserveSeat: seat=1 ACQUIRED -> Reserved -> FAIL -> RELEASE
[21:52:58.504] [Thread 14] ReserveSeat: seat=1 ACQUIRED -> Reserved -> FAIL -> RELEASE

=== Итоги ===
Успешных броней одного и того же места: 1 из 5
Итоговый статус места в репозитории: Reserved
SemaphoreSlim(1) обеспечил взаимное исключение: гонка не проявилась.
```

Ответы на 4 вопроса:

| Вопрос | lock (Monitor) | SemaphoreSlim(1,1) |
| --- | --- | --- |
| Что синхронизирует? | Взаимное исключение над блоком кода в пределах **одного процесса** (обёртка над `Monitor.Enter/Exit`) | То же взаимное исключение (при счётчике 1), но через счётчик разрешений; поддерживает `await` внутри защищённого участка |
| Между процессами? | Нет — объект блокировки существует только в памяти процесса | Нет в текущем виде (`new SemaphoreSlim(...)`, локальный); именованный `Semaphore`/`Mutex` — да, но `SemaphoreSlim` — только внутрипроцессный |
| Подходит для сценария? | Да — весь код критической секции синхронный (нет `await` внутри), `lock` проще и дешевле | Да, и даже удобнее, если бы критическая секция сама делала `await` (например, реальный асинхронный I/O к БД) — здесь это не требовалось, добавлено для сравнения |
| Отличие от lock | `lock` нельзя обернуть вокруг `await` (ошибка компиляции CS1996), не считает "сколько" потоков внутри — либо 0, либо 1; `SemaphoreSlim` — счётчик, можно пропускать N потоков одновременно (`new SemaphoreSlim(N)`), и внутри можно `await` | — |

## Часть 2. Синхронизация времени

### Требования 1-2: моделирование и демонстрация проблемы

`src/TicketSales.Client/Program.cs` спрашивает при старте смещение часов
клиента в секундах и хранит его как `TimeSpan clockOffset`; "локальное время"
клиента всегда вычисляется как `DateTime.UtcNow + clockOffset`
(`TimeSynchronizer.ApplyOffset`, [TimeSynchronizer.cs](src/TicketSales.Client/TimeSynchronizer.cs)).
Пункт меню 5 просто печатает это смещённое время — без синхронизации оно
отличается от времени сервера ровно на введённое смещение.

### Требования 3-6: запрос времени, RTT, поправка

Операция `GetServerTime` (DTO `GetServerTimeRequestDto`/`GetServerTimeResponseDto`,
[`GetServerTimeHandler`](src/TicketSales.Server/Dispatching/Handlers/GetServerTimeHandler.cs))
возвращает `DateTime.UtcNow` сервера, с необязательной искусственной задержкой
перед ответом (Требование 7) — второй аргумент командной строки сервера,
`dotnet run --project src/TicketSales.Server -- <port> <delayMs>`.

Клиент (`HandleSynchronizeTime` в `Program.cs`) фиксирует время отправки по
своим (смещённым) часам, измеряет RTT по разнице `DateTime.UtcNow` до и после
`SendAsync`, и считает:

```csharp
// src/TicketSales.Client/TimeSynchronizer.cs
public static TimeSpan CalculateOffset(DateTime serverTimeUtc, DateTime requestSentAtClientClock, TimeSpan rtt)
{
    var estimatedTrueTimeAtRequest = requestSentAtClientClock + TimeSpan.FromTicks(rtt.Ticks / 2);
    return serverTimeUtc - estimatedTrueTimeAtRequest;
}
```

т.е. предполагается, что момент, которому соответствует `serverTime`, — это
середина интервала запрос→ответ (Требование 6). `CorrectedTime = ApplyOffset(LocalTime, Offset)`.
Проверено юнит-тестами на собственных числовых примерах из lab3.md
(`tests/TicketSales.Tests/TimeSynchronizerTests.cs`):
клиент с часами `+7s` и мгновенным ответом сервера даёт `offset = -7s`;
пример "отправлено 10:00:00, время сервера 10:00:01, получено 10:00:02"
(RTT=2s) даёт `offset = 0`, так как середина RTT (10:00:01) в точности
совпала с временем сервера.

### Проверка точности (Требование 9 / вывод)

Три реальных прогона с разной искусственной задержкой на сервере показывают,
что чем больше RTT, тем больше остаточная погрешность после синхронизации —
и погрешность растёт примерно как `delay / 2`, потому что искусственная
задержка в `GetServerTimeHandler` асимметрична: сервер спит **перед** тем как
взять `DateTime.UtcNow`, а не "в середине" обработки, поэтому реальная точка,
которой соответствует `serverTime`, всегда ближе к моменту получения ответа,
чем к геометрической середине RTT, которую использует формула.

- **Эксперимент 1** (offset=+7s, delay=1000ms): вычисленная поправка
  `-6493 ms` вместо истинных `-7000 ms` → ошибка **≈507 мс**.
- **Эксперимент 2** (offset=-5s, delay=0ms, только реальная сеть — localhost):
  вычисленная поправка `+5018 ms` вместо истинных `+5000 ms` → ошибка
  **≈18 мс**, почти точно (RTT всего 58 мс).
- **Эксперимент 3** (offset=+7s, delay=3000ms): вычисленная поправка
  `-5490 ms` вместо истинных `-7000 ms` → ошибка **≈1510 мс**, то есть
  примерно `delay/2 = 1500 мс` — систематическая ошибка растёт линейно с
  задержкой, как и предсказывает модель асимметрии.

Вывод: без искусственной задержки (эксперимент 2) оценка почти идеальна —
RTT маленький и симметричный, поэтому середина интервала действительно
близка к моменту снятия `serverTime`. С ростом задержки (эксперименты 1 и 3)
точность падает пропорционально, потому что реальная асимметрия обработки
запроса на сервере нарушает предположение "задержка туда = задержка
обратно". Это прямая иллюстрация контрольного вопроса 15: сетевая задержка
снижает точность синхронизации, так как модель "время сервера соответствует
середине RTT" — лишь приближение, а не гарантия.

## Контрольные вопросы — короткие ответы, специфичные для этого проекта

- **Почему `lock` устраняет гонку из ЛР №2:** он гарантирует, что "проверить
  `Free` → записать `Reserved`" выполняется как одна неделимая операция —
  второй поток физически не может начать проверку, пока первый не закончил
  запись (см. реальный лог выше: все FAIL происходят *после* SUCCESS первого
  победителя, в ту же миллисекунду, но строго по очереди).
- **Почему RTT снижает точность синхронизации:** поправка вычисляется в
  предположении, что путь "туда" и "обратно" занимают одинаковое время и что
  `serverTime` соответствует ровно середине этого интервала; реальная
  асимметрия (как в примере выше, где искусственная задержка стоит перед
  измерением времени, а не посередине) прямо уменьшает точность оценки.
