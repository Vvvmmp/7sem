# Многопоточность и асинхронность в TicketSales (ЛР №2)

Документ фиксирует все места кодовой базы, где задействованы многопоточность,
`Task`/`async`, конкурентный доступ к общим данным, а также намеренно
воспроизведённую проблему Race Condition. Синхронизация в этой лабораторной
работе **не реализуется** — это задача ЛР №3.

## 1. Параллельная обработка клиентских подключений

**[`src/TicketSales.Server/Networking/TcpServer.cs`](src/TicketSales.Server/Networking/TcpServer.cs)**

```csharp
while (!cancellationToken.IsCancellationRequested)
{
    var client = await _listener.AcceptTcpClientAsync(cancellationToken);
    _ = HandleClientAsync(client, cancellationToken); // fire-and-forget Task
}
```

Каждое новое TCP-подключение запускается как отдельная асинхронная задача
(`Task`) и не ожидается (`_ =`) в цикле приёма. Поэтому сервер не блокируется
на одном клиенте и может параллельно обслуживать произвольное число
подключений — именно здесь реализована "параллельная обработка нескольких
клиентских запросов" из ТЗ.

## 2. Обработка запросов одного подключения

**[`src/TicketSales.Server/Networking/ClientSession.cs`](src/TicketSales.Server/Networking/ClientSession.cs)**

Внутри одного подключения запросы читаются и обрабатываются строго
последовательно (`await reader.ReadLineAsync()` → `await _dispatcher.DispatchAsync()`
→ `await JsonLineProtocol.SendAsync()`), но эта последовательность выполняется
в собственном `Task` подключения, поэтому **разные клиенты работают
конкурентно друг с другом**.

Добавлено логирование начала/конца обработки каждого запроса
(`Log(...)`, метка времени `HH:mm:ss.fff` + `Environment.CurrentManagedThreadId`).
По этим меткам видно, что интервалы обработки запросов от разных клиентов
пересекаются во времени и выполняются на разных потоках пула — это способ
"определить, действительно ли запросы обрабатываются одновременно" (п. 2 ТЗ),
в отличие от простого визуального совпадения в консоли.

## 3. Асинхронный конвейер диспетчеризации

- **[`IOperationHandler.cs`](src/TicketSales.Server/Dispatching/IOperationHandler.cs)** —
  `Task<object> HandleAsync(JsonElement payload)` вместо синхронного `Handle`.
- **[`OperationDispatcher.cs`](src/TicketSales.Server/Dispatching/OperationDispatcher.cs)** —
  `DispatchAsync` последовательно `await`-ит `handler.HandleAsync(...)`,
  прокидывая асинхронность от сессии клиента до сервиса.
- **4 обработчика** (`GetEventsHandler`, `ReserveSeatHandler`, `BuyTicketHandler`,
  `CancelTicketHandler`) — тонкие `async` обёртки над `ITicketSalesService`.

Раньше диспетчеризация была полностью синхронной внутри уже асинхронного
цикла подключения; теперь весь путь запроса — от чтения строки до вызова
бизнес-логики — построен на `Task`/`async`/`await`, как и требует ТЗ ("task и
асинхронный метод"), а не только внешняя обёртка вокруг синхронного кода.

## 4. Общий ресурс и место Race Condition

**[`src/TicketSales.Server/Domain/Services/TicketSalesService.cs`](src/TicketSales.Server/Domain/Services/TicketSalesService.cs) → `ReserveSeat`**

Общий ресурс — состояние места (`Seat.Status`) в `_seatRepository`, к которому
параллельно обращаются все клиенты, бронирующие места одного события.

```csharp
if (seat.Status != SeatStatus.Free)         // ЧТЕНИЕ (check)
{
    throw new ValidationException(...);
}

await Task.Delay(5000);                     // искусственно расширенное окно гонки

seat.Status = SeatStatus.Reserved;          // ЗАПИСЬ (act)
_seatRepository.Update(seat);
```

Это классический **TOCTOU (time-of-check to time-of-use)**: проверка статуса
и его запись — две раздельные, ничем не защищённые операции. Если несколько
запросов на одно и то же место окажутся между проверкой и записью
одновременно, каждый из них увидит `Free` и каждый успешно "забронирует"
место.

`await Task.Delay(5000)` — не причина гонки, а лишь усилитель окна. Гонка
реальна и без него: 5 автоматических клиентов из `TicketSales.RaceDemo`
(они шлют запросы через `Task.WhenAll`, то есть почти одновременно и без
участия человека) стабильно получали 5 из 5 "успешных" броней одного места
даже при полностью убранной задержке — потому что здесь работает не
кооперативный async-переход между потоками, а **настоящий параллелизм
уровня ОС**: `TcpServer` поднимает по одному `Task`/потоку пула на каждое
подключение, и на многоядерном CPU эти потоки в буквальном смысле выполняют
код `ReserveSeat` одновременно на разных ядрах, приходя к проверке `Free`
почти в один и тот же момент (все 5 запросов проделывают одинаковый по
стоимости путь — десериализация JSON, поиск события/места).

Секундная задержка (5000 мс) нужна для другого сценария —
**демонстрации гонки руками**, двумя независимыми процессами
`TicketSales.Client` (см. раздел 6.2 ниже), а не автотестом/скриптом.
Человек физически не может ввести 4 поля и нажать Enter в двух терминалах
с разницей меньше секунды-двух, поэтому без задержки такого масштаба окно
гонки для ручной демонстрации слишком мало — 150 мс или их отсутствие
достаточно для `RaceDemo`, но не для рук.

Логирование до и после критической секции (с той же меткой времени/ID
потока) наглядно показывает, что несколько потоков одновременно проходят
проверку `Free`, прежде чем кто-либо из них произведёт запись.

### Почему `ConcurrentDictionary` не спасает

**[`src/TicketSales.Server/Storage/InMemory/InMemoryRepository.cs`](src/TicketSales.Server/Storage/InMemory/InMemoryRepository.cs)**

Хранилище использует `ConcurrentDictionary<int, TEntity>` и `Interlocked.Increment`
для генерации ID — это защищает **отдельные** операции `Add`/`GetById`/`Update`
от повреждения данных структуры словаря. Но `TicketSalesService.ReserveSeat`
выполняет составную последовательность из нескольких таких операций
(`GetById` → бизнес-проверка → `Update`), а атомарность всей последовательности
`ConcurrentDictionary` не гарантирует. Отсюда и race condition: потокобезопасный
контейнер не равен потокобезопасной бизнес-операции над ним.

## 5. Асинхронность на стороне клиента

**[`src/TicketSales.Client/NetworkClient.cs`](src/TicketSales.Client/NetworkClient.cs)** —
`ConnectAsync` (с таймаутом через `Task.WhenAny(connectTask, Task.Delay(timeoutMs))`)
и `SendAsync` — независимый экземпляр `NetworkClient` на каждое подключение,
что позволяет одному процессу держать множество параллельных соединений с
сервером.

## 6. Как увидеть гонку своими глазами

### 6.1. Автоматически — проект `TicketSales.RaceDemo`

**[`src/TicketSales.RaceDemo/Program.cs`](src/TicketSales.RaceDemo/Program.cs)**

Новый консольный проект — практическая часть эксперимента:

1. Поднимает `TcpServer` в процессе с реальными данными из `SeedData`.
2. Через `Task.WhenAll` параллельно запускает 5 независимых `NetworkClient`
   ("пять разных клиентов"), каждый из которых вызывает `ReserveSeat` для
   **одного и того же** `seatId`.
3. Печатает результат каждого клиента и итоговую сводку: сколько "успешных"
   броней вернул сервер и сколько билетов реально создано на одно место.

Запуск:

```bash
dotnet run --project src/TicketSales.RaceDemo
```

Наблюдаемый результат (фрагмент реального прогона):

```
[14:25:31.939] [Thread 15] ReserveSeat: seat=1 проверка статуса -> Free
[14:25:31.939] [Thread 14] ReserveSeat: seat=1 проверка статуса -> Free
[14:25:31.939] [Thread 16] ReserveSeat: seat=1 проверка статуса -> Free
[14:25:31.939] [Thread 13] ReserveSeat: seat=1 проверка статуса -> Free
[14:25:31.939] [Thread 7]  ReserveSeat: seat=1 проверка статуса -> Free
...
Успешных броней одного и того же места: 5 из 5
Итоговый статус места в репозитории: Reserved
Количество созданных билетов на это место: 5

RACE CONDITION ВОСПРОИЗВЕДЕНА: одно и то же место забронировано более одного раза.
```

Все 5 потоков одновременно (одна и та же метка времени) прошли проверку
`Free`, после чего каждый независимо записал `Reserved` и создал билет —
одно физическое место оказалось продано 5 разным покупателям.

### 6.2. Вручную — два окна `TicketSales.Client` без какого-либо теста

Показывает ту же гонку "живьём", без единой строчки автоматизации — двумя
обычными запусками консольного клиента рядом друг с другом. Именно для
этого сценария и нужна секундная задержка `await Task.Delay(5000)` в
`ReserveSeat`: она держит место "как бы свободным" достаточно долго, чтобы
человек успел вручную отправить второй запрос, пока первый ещё не записал
результат.

1. Запустить сервер в одном терминале:

   ```bash
   dotnet run --project src/TicketSales.Server -- 5050
   ```

2. Открыть **два** отдельных терминала рядом (side by side) и в каждом
   запустить клиент, подключив оба к одному серверу (`127.0.0.1`, порт `5050`):

   ```bash
   dotnet run --project src/TicketSales.Client
   ```

3. В **терминале A** выбрать пункт `2` (Забронировать место) и быстро ввести:
   `Id события: 1`, `Id места: 1`, любое ФИО, любой email (например
   `a@test.com`) — и нажать Enter на последнем поле, чтобы запрос ушёл.
4. Сразу после этого (у вас есть ~5 секунд — время задержки) переключиться в
   **терминал B**, тоже выбрать пункт `2` и ввести **те же** `Id события: 1`,
   `Id места: 1`, другое ФИО/email (например `b@test.com`), отправить.
5. Оба терминала должны получить успех:

   ```
   Место забронировано. TicketId = 1     (терминал A)
   Место забронировано. TicketId = 2     (терминал B)
   ```

   Это и есть визуальное доказательство race condition: одно и то же место
   `Id=1` только что "успешно" забронировали два разных человека. В логе
   сервера (в его собственном терминале) видно, что оба запроса прошли
   проверку `seat=1 проверка статуса -> Free` практически подряд, а затем
   оба записали `-> Reserved`.
6. Если не успеть уложиться в 5-секундное окно (например, отвлеклись на
   ввод полей), второй терминал получит ожидаемо честный `Ошибка: Место уже
   занято` — тогда просто повторите: выберите `2` в обоих терминалах ещё
   раз для другого свободного `seatId` (например `2`) и постарайтесь
   отправить оба запроса быстрее.

## 7. Что намеренно НЕ исправлено

- Аналогичное незащищённое окно "чтение → изменение статуса → запись" есть и
  в `BuyTicket` (`seat.Status = SeatStatus.Sold`) и в `CancelTicket`
  (`seat.Status = SeatStatus.Free`) — они не тронуты и не являются целью этой
  ЛР, но подвержены той же природе проблемы.
- Никакая блокировка (`lock`, `SemaphoreSlim`, `Monitor`, атомарный
  compare-and-swap над статусом места и т.п.) не добавлена — это предмет
  следующей лабораторной работы.
