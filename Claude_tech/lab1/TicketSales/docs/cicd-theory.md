# CI/CD: теория простым языком

## Зачем это нужно

Без автоматизации путь от правки кода до работающего приложения выглядит так: поправил код → вспомнил собрать → вспомнил запустить тесты → собрал Docker-образ → выкатил в Kubernetes. На каждом шаге можно ошибиться: забыть тесты, собрать образ из старого кода, выкатить сломанную версию. Чем чаще правки, тем больше ошибок.

**CI/CD** — это договоренность «все эти шаги выполняет машина, одинаково и каждый раз». Человек только делает `git push`.

## Три понятия, которые путают

| Термин | Что делает | Аналогия |
|---|---|---|
| **Continuous Integration** (непрерывная интеграция) | После каждого изменения кода автоматически: получить код → собрать → прогнать тесты. Цель — сразу узнать, что изменение что-то сломало | Корректор проверяет каждую страницу, как только автор ее сдал |
| **Continuous Delivery** (непрерывная доставка) | CI + автоматически подготовить готовый к выпуску артефакт (у нас — Docker-образ). Выкатка — по кнопке, после ручного подтверждения | Книга отпечатана и лежит на складе, ждет решения «отправлять» |
| **Continuous Deployment** (непрерывное развертывание) | Delivery + выкатка в рабочую среду **без человека**, если все проверки пройдены | Книга сама уезжает в магазины сразу после печати |

Единственное различие Delivery и Deployment — **кто нажимает кнопку «выкатить»**: человек или pipeline. В этой лабе реализован Deployment: после зеленых тестов новая версия сама попадает в Kubernetes.

## Pipeline (конвейер)

Pipeline — цепочка этапов (stage), где каждый запускается только если предыдущий прошел. Упал этап — конвейер остановился, дальше версия не едет.

```
Checkout → Restore → Build → Test → Package → Deploy → Verify
 получить   скачать   собрать  тесты  Docker-    обновить  проверить,
  код       пакеты                    образ      в k8s     что работает
```

Главная идея: **неисправная версия не должна дойти до Deploy**. Поэтому тесты стоят до Package: упавший тест останавливает конвейер, образ не создается, в кластере остается старая рабочая версия.

## Jenkins

Jenkins — программа-«дежурный», которая выполняет pipeline: умеет получать код из Git, запускать команды (`dotnet`, `docker`, `kubectl`), показывать лог каждого запуска (Console Output) и итоговый статус (Success / Failed).

- **Job** — одно задание в Jenkins (у нас `TicketSales-CICD`).
- **Jenkinsfile** — текстовый файл с описанием pipeline. Лежит в Git рядом с кодом, значит, процесс сборки версионируется так же, как код: изменили конвейер — это видно в истории коммитов.
- **Pipeline script from SCM** — режим, где Jenkins сам берет Jenkinsfile из репозитория, а не из настроек в веб-интерфейсе.
- **Build number** — порядковый номер запуска (1, 2, 3…). Мы используем его как тег образа: `ticketsales-server:7` — это образ, собранный седьмым запуском. Так всегда видно, какой код сейчас в кластере, а тег `latest` такого не показывает.

### Как Jenkins узнает о новом коммите

| Способ | Как работает |
|---|---|
| Ручной запуск | Нажали «Build Now» |
| **Poll SCM** | Jenkins раз в N минут спрашивает Git «есть новое?» (`H/2 * * * *` — примерно раз в 2 минуты; `H` — случайная минута, чтобы задания не стартовали одновременно) |
| Webhook | Git сам сообщает Jenkins о push. Быстрее, но Jenkins должен быть доступен из интернета — для локальной лабы не подходит |

## Что происходит на каждом этапе

| Этап | Команда | Зачем |
|---|---|---|
| Checkout | `checkout scm` | Взять ровно тот коммит, который запустил pipeline |
| Restore | `dotnet restore` | Скачать NuGet-пакеты. Отдельный этап, чтобы проблемы с зависимостями отличались от ошибок компиляции |
| Build | `dotnet build -c Release --no-restore` | Убедиться, что код компилируется. `--no-restore` — пакеты уже скачаны |
| Test | `dotnet test` | Проверить логику. Падение любого теста = Failed |
| Package | `docker build -t имя:НОМЕР .` | Упаковать приложение в образ — неизменяемый артефакт «собрано и проверено» |
| Deploy | `kubectl set image` + `rollout status` | Заменить образ в Deployment; Kubernetes запускает новые Pod и только потом гасит старые (RollingUpdate). `rollout status` ждет конца и возвращает ошибку, если новые Pod не поднялись |
| Verify | запрос к приложению | «Команда прошла» ≠ «приложение работает»; проверяем реальный ответ сервера |

## Типичные подводные камни

- **Окружение Jenkins ≠ ваш терминал.** Jenkins может работать от другого пользователя с другим `PATH`, без доступа к Docker и без вашего `~/.kube/config`. Поэтому в Jenkinsfile задан `PATH` и явно указан kube-контекст.
- **Образ на вашем компьютере ≠ образ в кластере.** Kubernetes из Docker Desktop использует тот же Docker Engine, поэтому собранный образ ему виден сразу. В Minikube, у которого свой Docker, образ пришлось бы загружать командой `minikube image load`.
- **Секреты нельзя класть в Git и Jenkinsfile.** Пароль БД приложения лежит в Kubernetes Secret; в Jenkinsfile только тестовый пароль локальной БД для тестов (он же зашит в тестах).
- **Тесты, которым нужна БД.** Pipeline сам поднимает PostgreSQL перед тестами и гасит после (`post { always }`) — даже если тесты упали.

## Ограничения этого pipeline

- Jenkins и кластер локальные, один агент: нет параллельных сборок на разных машинах.
- Нет отката: при провале Deploy старые Pod продолжают работать (RollingUpdate их не трогает), но образ-неудачник остается в Deployment до следующего запуска.
- Poll SCM — задержка до пары минут; webhook ее убирает, но требует публичного адреса.
- Образ хранится только локально, без registry — подходит для лабы, в реальности образ пушат в реестр.
