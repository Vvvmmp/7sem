**Теоретические сведения**

В предыдущих ЛР основное состояние приложения могло храниться в памяти сервера, где архитектура приложения имела вид:

![](data:image/png;base64...)

В ЛР №4 необходимо добавить базу данных:

![](data:image/png;base64...)

Клиент не должен обращаться к базе данных напрямую. Клиент отправляет запрос серверу, а сервер:

* принимает запрос;
* выполняет необходимые действия;
* обращается к базе данных;
* получает или изменяет данные;
* возвращает результат клиенту.

То есть, сервер выступает посредником между клиентом и базой данных.

**База данных (Database)** – организованная совокупность данных, предназначенная для хранения и обработки информации.

**Система управления базами данных (СУБД)** – программное обеспечение, обеспечивающее создание, хранение, изменение и получение данных из базы данных.

Можно использовать любую СУБД, подходящую для реализации проекта и имеющую возможность взаимодействия с C#, например:

* PostgreSQL;
* MySQL;
* Microsoft SQL Server;
* SQLite.

Сервер должен выполнять операции с БД вместо хранения основного состояния предметной области только в памяти. Конкретный состав таблиц определяется предметной областью. Не требуется реализовывать сложную промышленную БД. Необходимо создать структуру, достаточную для выполнения операций ЛР.

В распределенном приложении несколько клиентов могут одновременно отправлять серверу запросы, изменяющие одни и те же данные, например:

![](data:image/png;base64...)

Пусть в системе имеется один доступный ресурс Available = 1. Два клиента одновременно пытаются получить его. Если сервер выполняет операции без необходимой синхронизации, возможно некорректное поведение:

Client 1 → read Available = 1

Client 2 → read Available = 1

Client 1 → reserve

Client 2 → reserve

В результате один ресурс может оказаться выдан двум клиентам. В ЛР №3 подобная проблема рассматривалась на уровне общего состояния приложения, а в данной работе необходимо учитывать два уровня:

1. Синхронизацию выполнения кода сервера.
2. Согласованность изменений в базе данных.

В данной лабораторной работе для синхронизации критической секции используется механизм lock.

**Транзакция (Transaction)** – последовательность операций с базой данных, рассматриваемая как единое целое, где все необходимые изменения выполняются успешно, либо изменения отменяются.

**COMMIT** – подтверждение транзакции.

**ROLLBACK** – отмена транзакции.

Без транзакции возможна ситуация:

Create Order → SUCCESS

Update Stock → ERROR

В базе данных останется созданный заказ, но количество товара не изменится – получается противоречивое состояние, а с транзакцией:

BEGIN

↓

Create Order

↓

Update Stock

↓

ERROR

↓

ROLLBACK

После ROLLBACK база возвращается к состоянию, существовавшему до начала транзакции.

Важно различать два механизма: lockиспользуется для синхронизации выполнения кода внутри приложения:

![](data:image/png;base64...)

Транзакция используется для обеспечения согласованности группы операций с базой данных:

BEGIN

↓

Operation 1

↓

Operation 2

↓

COMMIT / ROLLBACK

lock не является заменой транзакции, а транзакция не является заменой lock. Они решают разные задачи и могут использоваться совместно.

Запустите:

* два клиента.

Оба клиента должны выполнить одну и ту же операцию над одним ресурсом. Запросы должны выполняться одновременно или с минимальным временным интервалом.

**Требование 3. Использование lock**.

Необходимо определить критическую секцию и защитить ее с помощью lock:

lock (syncObject)

{

check resource;

if (resource available)

{

reserve resource;

return SUCCESS;

}

return FAIL;

}

В критическую секцию необходимо поместить все взаимосвязанные действия, которые должны выполняться атомарно относительно других потоков. Не помещать под lock весь метод без необходимости.

**Требование 4. Проверка результата.**

Пусть имеется Resource = 1. Два клиента одновременно выполняют:

Client 1 → Reserve

Client 2 → Reserve

Корректный результат:

Client 1 → SUCCESS

Client 2 → FAIL

или:

Client 1 → FAIL

Client 2 → SUCCESS

Но результат:

Client 1 → SUCCESS

Client 2 → SUCCESS

при наличии одного ресурса является некорректным.

**Требование 5. Логирование.**

[10:15:01.131] Client 1 → Check resource

[10:15:01.135] Client 1 → SUCCESS

[10:15:01.140] Client 1 → UNLOCK

[10:15:01.141] Client 2 → START Reserve

[10:15:01.145] Client 2 → LOCK

[10:15:01.146] Client 2 → Check resource

[10:15:01.150] Client 2 → FAIL

[10:15:01.151] Client 2 → UNLOCK

В журнале необходимо отображать:
