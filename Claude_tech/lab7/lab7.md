**Теоретические сведения**

В распределенной системе несколько узлов могут одновременно работать с одной системой данных или выполнять общую задачу, где каждый узел является отдельным компонентом системы. Проблема возникает, когда узлам необходимо принять одно общее решение, например, какой узел должен быть лидером или какое значение состояния системы считать актуальным? Если каждый узел принимает решение самостоятельно, состояние системы может стать противоречивым.

**Консенсус (Consensus)** – это процесс, позволяющий нескольким узлам распределенной системы прийти к согласованному решению, то есть:

![](data:image/png;base64...)

Например, пять узлов должны определить Leader = Node 5, если большинство узлов согласилось с этим решением, система считает его принятым.

**Лидре (Leader)** – узел, которому в распределенной системе может быть поручена координация определенной операции, например:

![](data:image/png;base64...)

Лидер может:

* координировать операции;
* распространять информацию;
* предлагать изменения состояния;
* инициировать принятие решений.

При этом лидер не должен рассматриваться как единственный узел системы, если он выходит из строя, распределенная система должна иметь возможность выбрать нового лидера.

**Выбор лидера (Leader election)** – процесс определения узла, который будет выполнять роль лидера.

В ЛР используется простое правило – лидером становится доступный узел с наибольшим идентификатором, например:

Node 1 — AVAILABLE

Node 2 — AVAILABLE

Node 3 — AVAILABLE

Node 4 — AVAILABLE

Node 5 — AVAILABLE

Результат: Leader = Node 5, если Node 5 становится недоступным, то:

Node 1 — AVAILABLE

Node 2 — AVAILABLE

Node 3 — AVAILABLE

Node 4 — AVAILABLE

Node 5 — FAILED

новым лидером становится Leader = Node 4.

Каждый узел должен иметь состояние, например, AVAILABLE / FAILED, а также роль LEADER / FOLLOWER. То есть, состояние узла может выглядеть следующим образом:

Node 3

Status: AVAILABLE

Role: FOLLOWER

или:

Node 5

Status: FAILED

Role: LEADER

Распределенная система должна уметь определить, что узел перестал отвечать. В ЛР это можно реализовать с помощью простого механизма **heartbeat**, например:

Node 1 → Node 5: HEARTBEAT?

Node 5 → Node 1: ALIVE

Если ответ не поступает:

Node 1 → Node 5: HEARTBEAT?

Node 5 → NO RESPONSE

узел может считаться недоступным.

Для ЛР не требуется реализовывать полноценный промышленный Failure detector, отказ можно моделировать:

* изменением состояния узла;
* остановкой обработки;
* искусственным исключением;
* прекращением ответа на heartbeat.

Одно из основных понятий ЛР – **большинство (Majority)**. Если в системе 5 узлов, то большинство – 3 узла. Если 4 узла, то большинство – 3 узла.

Для пяти узлов:

|  |  |  |
| --- | --- | --- |
| **Доступные узлы** | **Большинство** | **Консенсус** |
| 5 | 3 | возможен |
| 4 | 3 | возможен |
| 3 | 3 | возможен |
| 2 | 3 | невозможен |
| 1 | 3 | невозможен |

То есть система может продолжать принимать решения при отказе части узлов, пока сохраняется необходимое большинство.

В ЛР один узел может предложить решение, например:

Leader:

ConfigurationVersion = 15

Другие узлы голосуют:

Node 1 → YES

Node 2 → YES

Node 3 → YES

Node 4 → NO

Node 5 → NO RESPONSE

Количество положительных голосов равно 3. При пяти узлах это большинство, а значит CONSENSUS ACHIEVED.

Если доступно недостаточно узлов, большинство получить невозможно, например:

Node 1 → YES

Node 2 → YES

Node 3 → NO RESPONSE

Node 4 → NO RESPONSE

Node 5 → NO RESPONSE

Получено только 2 / 5. Большинство 3 / 5, следовательно, CONSENSUS NOT ACHIEVED.

В ЛР используется простая модель, но ее элементы соответствуют реальным механизмам распределенного консенсуса.

|  |  |
| --- | --- |
| **Лабораторная** | **Реальные алгоритмы** |
| Node | Участник распределенной системы |
| Leader | Leader / координатор |
| Leader Election | Выбор лидера |
| Vote | Голосование |
| Majority | Quorum |
| Agreement | Согласованное решение |
| Node Failure | Отказ узла |
| New Leader | Повторный выбор лидера |

Реализованная модель хорошо связывается с **Raft**, так как он явно разделяет роли узлов и предусматривает выбор лидера.

**Paxos** использует другую модель согласования, основанную на ролях и предложениях, однако также решает задачу достижения согласованного решения при отказах.

**Zab** используется в Apache ZooKeeper и ориентирован на согласование состояния и упорядочивание изменений в распределенной системе.

В ЛР не нужно реализовывать алгоритмы полностью, нужно понимать, какие проблемы они решают и какие элементы ЛР соответствуют основным идеям.

**Задание для выполнения**

**Часть 1. Создание нескольких узлов**

Дополнить проект взаимодействующими узлами, где минимально использовать 5 узлов: Node 1, Node 2, Node 3, Node 4, Node 5.

Каждый узел должен иметь:

* уникальный идентификатор;
* состояние;
* роль;
* информацию о других узлах;
* возможность отправлять сообщения;
* возможность принимать сообщения;
* возможность изменять свое состояние.

**Часть 2. Реализация выбора лидера**

Необходимо реализовать механизм Leader election, где лидером становится доступный узел с максимальным ID. Результат выбора лидера должен быть записан в журнал:

[14:20:10.120] Election started

[14:20:10.150] Node 1 AVAILABLE

[14:20:10.151] Node 2 AVAILABLE

[14:20:10.152] Node 3 AVAILABLE

[14:20:10.153] Node 4 AVAILABLE

[14:20:10.154] Node 5 AVAILABLE

[14:20:10.160] Node 5 elected as LEADER

**Часть 3. Обнаружение отказа лидера**

Необходимо смоделировать отказ текущего лидера, например, Node 5 → LEADER. После этого Node 5 → FAILED. Реализовать проверку доступности узлов, где нужно использовать heartbeat:

Node 2 → HEARTBEAT → Node 5

Node 5 → NO RESPONSE

После обнаружения отказа необходимо зафиксировать Node 5 → FAILED в журнале.

**Часть 4. Повторный выбор лидера**

После отказа лидера запустить процедуру повторного выбора, где до отказа:

Node 1 — FOLLOWER

Node 2 — FOLLOWER

Node 3 — FOLLOWER

Node 4 — FOLLOWER

Node 5 — LEADER

После отказа:

Node 1 — FOLLOWER

Node 2 — FOLLOWER

Node 3 — FOLLOWER

Node 4 — LEADER

Node 5 — FAILED

В журнале:

[14:25:01] Node 5 is LEADER

[14:25:05] Node 5 heartbeat timeout

[14:25:06] Election started

[14:25:06] Node 5 excluded

[14:25:07] Node 4 elected as LEADER

Убедиться, что одновременно существует только один Leader.

**Часть 5. Реализация голосования и консенсуса**

После выбора лидера реализовать механизм предложения и голосования. Лидер должен иметь возможность предложить некоторое значение, например, ConfigurationVersion = 10 или значение, связанное с предметной областью. Лидер отправляет предложение остальным узлам:

Leader → Node 1

Leader → Node 2

Leader → Node 3

Leader → Node 4

Каждый доступный узел возвращает YES или NO. После получения ответов лидер подсчитывает голоса, например:

Node 1 → YES

Node 2 → YES

Node 3 → YES

Node 4 → NO

Где результат, например, YES = 3 и NO = 1. При пяти узлах Majority = 3. Следовательно CONSENSUS ACHIEVED.

**Часть 6. Эксперименты с отказами и анализ**

Необходимо провести несколько экспериментов.

**Эксперимент 1. Все узлы доступны.**

При доступности 5 / 5 узлов необходимо:

* выбрать лидера;
* предложить значение;
* получить голоса;
* получить консенсус.

Ожидаемый результат CONSENSUS ACHIEVED.

**Эксперимент 2. Отказ одного узла.**

Например, Node 5 — FAILED. Остается 4 / 5 AVAILABLE, необходимо проверить:

* выполняется ли повторный выбор лидера;
* сохраняется ли большинство;
* достигается ли консенсус.

Ожидаемый результат CONSENSUS ACHIEVED.

**Эксперимент 3. Отказ двух узлов.**

Например, Node 4 — FAILED, Node 5 — FAILED. Остается 3 / 5 AVAILABLE. Необходимо проверить возможность достижения консенсуса. Ожидаемый результат CONSENSUS ACHIEVED.

**Эксперимент 4. Отказ трех узлов.**

Например:

Node 3 — FAILED

Node 4 — FAILED

Node 5 — FAILED

Остается 2 / 5 AVAILABLE. Необходимо выполнить попытку голосования. Ожидаемый результат CONSENSUS NOT ACHIEVED.

При этом приложение не должно принимать решение, если необходимого большинства нет.

Приложение должно корректно обрабатывать:

* недоступность одного узла;
* недоступность нескольких узлов;
* отказ текущего лидера;
* отсутствие ответа на heartbeat;
* невозможность связаться с узлом;
* отсутствие большинства;
* попытку голосования недоступного узла;
* повторный запуск выбора лидера;
* получение нескольких сообщений одновременно;
* ошибочное сообщение от узла.

Если лидер выходит из строя, система не должна аварийно завершаться, она должна попытаться выбрать нового лидера, если большинства узлов нет, система не должна объявлять консенсус достигнутым.

**Требование 3. Программа.**

* иметь уникальный ID;
* хранить свое состояние;
* иметь роль Leader или Follower;
* знать о других узлах;
* отвечать на heartbeat;
* обнаруживать отказ узла;
* участвовать в выборах;
* участвовать в голосовании;
* вести журнал и обрабатывать ошибки.

Leader должен:

* координировать выбор;
* предлагать значение;
* отправлять предложение узлам;
* принимать голоса и подсчитывать их;
* определять наличие большинства;
* объявлять результат консенсуса.

Follower должен:

* получать сообщения;
* отвечать на heartbeat;
* участвовать в выборах;
* принимать предложение;
* отдавать голос;
* сообщать о своем состоянии.

Клиент должен:

* подключаться к серверу;
* выполнять операции из предыдущих ЛР;
* инициировать операцию, приводящую к предложению изменения;
* отображать результат;
* отображать ошибки.
