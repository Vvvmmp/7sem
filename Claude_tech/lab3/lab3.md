**Критическая секция** (**Critical section**) – участок программы, в котором выполняются действия с общим ресурсом, не допускающие одновременного выполнения несколькими потоками.

Если два потока могут одновременно выполнять один и тот же общий ресурс, то возникает Race Condition. Необходимо обеспечить, чтобы в каждый момент времени только один поток выполнял критическую секцию. Это называется **взаимным исключением** (**Mutual exclusion**).

В C# существует несколько механизмов синхронизации.

**1. lock.**

Наиболее простой и распространенный вариант:

lock (syncObject)

{

// критическая секция

}

Пока один поток выполняет код внутри lock, другой поток, пытающийся получить тот же блокировочный объект, должен дождаться освобождения блокировки. Внутри lock должны находиться все действия, которые должны выполняться как единая неделимая операция.

**2. Monitor.**

Monitor предоставляет более низкоуровневый механизм управления блокировкой. Пример:

Monitor.Enter(syncObject);

try

{

// критическая секция

}

finally

{

Monitor.Exit(syncObject);

}

Конструкция lock фактически является удобным способом работы с механизмом Monitor.

**3. Mutex.**

Mutex позволяет синхронизировать доступ не только между потоками одного приложения, но и между процессами, например:

using Mutex mutex = new Mutex();

mutex.WaitOne();

try

{

// критическая секция

}

finally

{

mutex.ReleaseMutex();

}

Mutex имеет больший уровень накладных расходов, чем обычный lock, поэтому эти механизмы не являются полностью взаимозаменяемыми.

**4. SemaphoreSlim.**

SemaphoreSlim позволяет ограничить количество потоков, которые одновременно могут выполнять определенный участок кода, например:

SemaphoreSlim semaphore = new SemaphoreSlim(1);

await semaphore.WaitAsync();

try

{

// критическая секция

}

finally

{

semaphore.Release();

}

При значении 1 семафор можно использовать для организации взаимного исключения. При значении 2, например, одновременно могут находиться внутри защищенного участка не более двух задач.

**5. Interlocked.**

Interlocked используется для атомарного выполнения простых операций над переменными, например:

Interlocked.Increment(ref counter);

или:

Interlocked.Decrement(ref counter);

Этот механизм особенно удобен для простых счетчиков. Однако Interlocked не заменяет lock, если необходимо атомарно выполнить несколько взаимосвязанных действий.

**Часть 2. Синхронизация времени**

В распределенной системе сервер и клиенты работают на разных узлах. Каждый узел имеет собственные системные часы, но в реальной системе часы разных компьютеров могут немного отличаться.

**Требование 1. Моделирование рассинхронизации.**

TimeSpan.FromSeconds(-5);

Таким образом:

Client 1 → 10:00:07

**Требование 3. Реализация синхронизации времени.**

Необходимо реализовать простой механизм синхронизации. Клиент отправляет серверу запрос:

Client → TIME\_REQUEST

Сервер фиксирует свое время:

serverTime = DateTime.UtcNow

и возвращает его клиенту:

Server → TIME\_RESPONSE

serverTime

Клиент сравнивает полученное время со своим локальным временем.

**Требование 4. Расчет смещения часов.**

Пусть:

Client local time = 10:00:07

Server time = 10:00:00

Тогда:

Offset = ServerTime - ClientTime

Получаем Offset. Клиент сохраняет найденную поправку, где скорректированное время:

CorrectedTime =

LocalTime + Offset

**Требование 5. Учет задержки сети и измерение RTT.**

В предыдущем эксперименте предполагалось, что ответ сервера приходит практически мгновенно, но в распределенной системе это неверно. Между клиентом и сервером существует задержка:

![](data:image/png;base64...)

Время получения ответа отличается от времени его отправки. Поэтому необходимо измерить **RTT (Round-Trip Time)** – время полного прохождения запроса до сервера и обратно.

Перед отправкой запроса клиент фиксирует время:

DateTime requestTime = DateTime.UtcNow;

После получения ответа:

DateTime responseTime = DateTime.UtcNow;

Разница:

RTT = responseTime - requestTime

Для упрощенной модели можно предположить, что задержка в прямом и обратном направлении примерно одинакова:

Network delay ≈ RTT / 2

**Требование 6. Расчет скорректированного времени.**

Пусть клиент отправил запрос 10:00:00, а сервер сформировал ответ

10:00:01. Клиент получил ответ 10:00:02. И тогда:

RTT = 2 seconds

RTT / 2 = 1 second

Для простой оценки можно считать, что время сервера соответствует моменту примерно посередине интервала передачи. Клиент должен использовать эту оценку при расчете поправки.
