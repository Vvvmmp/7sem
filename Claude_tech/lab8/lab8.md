**Теоретические сведения**

В предыдущих ЛР было разработано распределенное приложение, компоненты которого взаимодействуют друг с другом. В обычном варианте запуска приложение зависит от установленного программного обеспечения, версии среды выполнения, конфигурации и доступности необходимых сервисов. Если на другом компьютере отсутствуют нужные компоненты или отличаются настройки окружения, запуск приложения может потребовать дополнительной подготовки. Контейнеризация позволяет упаковать приложение вместе с необходимыми компонентами окружения и запускать его в предсказуемой конфигурации.

**Docker** – платформа для создания, распространения и запуска контейнеризированных приложений.

Docker позволяет:

* собирать образы приложений;
* запускать приложения в контейнерах;
* изолировать процессы и файловые системы;
* задавать параметры запуска;
* подключать контейнеры к сетям;
* просматривать журналы;
* останавливать, запускать и удалять контейнеры.

**Контейнеризация** – способ упаковки приложения и необходимых ему компонентов окружения в изолированную среду выполнения.

Контейнер использует ядро операционной системы хоста, поэтому контейнеры обычно легче виртуальных машин. Контейнеризация позволяет уменьшить зависимость приложения от особенностей среды, в которой оно запускается, однако не устраняет все возможные различия в настройках, сетевом окружении и внешних сервисах.

**Docker Image** – образ, на основе которого создаются контейнеры.

Образ содержит файловую систему приложения и инструкции, необходимые для его запуска. В зависимости от способа сборки он может включать опубликованные файлы приложения, среду выполнения и другие зависимости. Один образ может использоваться для создания нескольких контейнеров, например, один образ серверного приложения можно использовать для запуска нескольких экземпляров сервера с разными параметрами конфигурации.

**Docker Container** – запущенный экземпляр образа.

Контейнер имеет собственное состояние выполнения, может запускаться, останавливаться и удаляться независимо от других контейнеров.

Удаление контейнера не означает автоматического удаления образа. При этом данные, записанные только в изменяемую файловую систему контейнера, могут быть потеряны при его удалении.

**Dockerfile** – текстовый файл с инструкциями для сборки образа.

В ЛР необходимо использовать следующие инструкции:

* FROM – определяет базовый образ;
* WORKDIR – задает рабочий каталог;
* COPY – копирует файлы в образ;
* RUN – выполняет команду во время сборки образа;
* EXPOSE – документирует порт, который использует приложение;
* ENTRYPOINT – определяет основную команду запуска контейнера.

Для приложений на C# можно использовать многоэтапную сборку, то есть на первом этапе выполняется сборка проекта с помощью .NET SDK, а на втором приложение запускается на подходящем образе .NET Runtime. Конкретные версии образов должны соответствовать используемой версии .NET и поддерживаемой среде выполнения.

**Docker Engine** – программная основа, обеспечивающая создание и управление образами, контейнерами, сетями и другими объектами Docker.

**Docker Desktop** – приложение, предоставляющее среду для работы с Docker на поддерживаемых настольных операционных системах.

В Windows Docker Desktop обычно используется для запуска Linux-контейнеров через подходящую виртуализированную среду.

Контейнер может запускать сервер, который ожидает подключения на определенном порту. Для доступа к приложению с хоста может потребоваться опубликовать порт контейнера, например, параметр запуска -p 8080:8080 связывает порт 8080 хоста с портом 8080 контейнера.

Следует различать:

* порт, на котором приложение ожидает подключения внутри контейнера;
* опубликованный порт, доступный с хоста;
* порт другого контейнера, доступный по внутренней сети Docker.

Само наличие инструкции EXPOSE не публикует порт автоматически.

**Docker Network** – механизм сетевого взаимодействия контейнеров.

Контейнеры, подключенные к общей пользовательской сети Docker могут взаимодействовать друг с другом. В стандартной конфигурации такой сети контейнеры могут обращаться к сервисам по их сетевым именам, например, Server → Database.

В контейнеризированном приложении сервер должен обращаться к базе данных по имени соответствующего сервиса и внутреннему порту, а не использовать localhost, если БД находится в другом контейнере. Адрес localhost внутри контейнера указывает на сам этот контейнер, а не на другой контейнер и не обязательно на компьютер пользователя.

**Docker Compose** – инструмент для описания и совместного запуска нескольких контейнеризированных сервисов, где конфигурация обычно хранится в файле compose.yaml.

В файле можно определить:

* сервисы;
* используемые образы или инструкции сборки;
* переменные окружения;
* опубликованные порты;
* сети;
* тома для хранения данных;
* зависимости между сервисами.

Запуск нескольких сервисов выполняется одной командой:

docker compose up --build

Остановка сервисов:

docker compose down

Docker Compose упрощает воспроизводимый запуск приложения, состоящего из нескольких компонентов.

**Environment Variables** – переменные окружения, с помощью которых приложению передаются параметры конфигурации.

Например, через переменные окружения можно задавать:

* адрес базы данных;
* порт сервера;
* режим работы приложения;
* параметры подключения к внешним сервисам.

Это позволяет использовать один и тот же образ в разных окружениях без изменения исходного кода.

Пароли, ключи и другие секреты нельзя помещать в общедоступный репозиторий или без необходимости включать в Docker-образ.

Docker позволяет просматривать стандартный вывод и сообщения об ошибках контейнеризированного приложения, для этого используется команда:

docker logs <container\_name>

Для наблюдения за журналом в режиме реального времени можно использовать:

docker logs -f <container\_name>

Журналы помогают определить, запустилось ли приложение, доступен ли нужный сервис и на каком этапе возникла ошибка.

Контейнеризация сама по себе не гарантирует отказоустойчивость приложения, если контейнер остановился, Docker позволяет запустить его повторно, однако это не означает, что все запросы будут обработаны без потерь или что данные автоматически восстановятся, необходимо различать:

* запуск приложения в контейнере;
* перезапуск контейнера;
* восстановление приложения после отказа;
* сохранность данных;
* автоматическое переключение на резервный компонент.

В ЛР требуется продемонстрировать остановку и повторный запуск контейнера, а также проанализировать последствия остановки для приложения.

Docker используется в работе для создания образов и запуска контейнеров. Kubernetes, который будет рассматриваться в следующей ЛР. В рамках ЛР №8 не требуется устанавливать Kubernetes, создавать кластер или описывать ресурсы Kubernetes.

**Часть 3. Docker Network и Docker Compose**

**Требование 1. Организация сети контейнеров и проверка сетевого взаимодействия.**

Необходимо настроить сетевое взаимодействие контейнеров, которые должны обмениваться данными. Для нескольких связанных контейнеров рекомендуется использовать пользовательскую сеть Docker или сеть, создаваемую Docker Compose. Проверить, что контейнеры могут обращаться к нужным сервисам.

Если сервер подключается к БД, в строке подключения следует использовать имя сервиса или контейнера в соответствующей сети и внутренний порт БД.

Нельзя автоматически заменять адрес сервиса на localhost: внутри контейнера этот адрес относится к самому контейнеру.

Проверить взаимодействие компонентов через Docker Network:

1. Запустить необходимые контейнеры.
2. Проверить доступность сервера.
3. Выполнить запрос клиента.
4. Проверить взаимодействие сервера с необходимыми сервисами.
5. Изучить журналы.
6. Зафиксировать результат.

Если взаимодействие не работает, то определить, связана ли ошибка с портами, сетевыми именами, настройками приложения или доступностью.

**Требование 2. Создание файла compose.yaml.**

Создать файл compose.yaml, описывающий необходимые сервисы приложения, где в файле следует указать:

* имена сервисов;
* образы или пути к сборке образов;
* необходимые порты;
* переменные окружения;
* сети;
* тома, если требуется сохранять данные;
* зависимости между сервисами, если они нужны.

Если используется БД, следует продумать сохранение ее данных при пересоздании контейнера, для этого можно использовать Docker Volume.

Указание зависимости между сервисами само по себе не гарантирует полной готовности зависимого сервиса к обработке запросов.

Приложение должно корректно обрабатывать ситуацию, когда необходимый сервис еще не готов.

После запуска убедиться, что необходимые сервисы созданы и запущены. Просмотреть состояния сервисов, журналов.

Проверить, что конфигурация позволяет повторно запускать приложение без ручного создания каждого контейнера.

**Требование 4. Проверка основных операций.**

После запуска приложения через Docker Compose выполнить не менее трех операций предметной области, где операции должны соответствовать варианту задания и использовать существующую бизнес-логику приложения.

Например, это могут быть:

* получение данных;
* создание или изменение записи;
* операция с общим ресурсом;
* обработка события;
* операция, связанная с состоянием узла, если она предусмотрена проектом.

Проверить, что результат соответствует ожидаемому и необходимые компоненты взаимодействуют корректно.

**Часть 4. Тестирование и итоговый анализ**

**Требование 1. Проверка штатной работы.**

Запустить приложение через Docker Compose и проверить его работу в штатном режиме, где следует убедиться, что:

* необходимые контейнеры запущены;
* сервер принимает запросы;
* необходимые компоненты доступны;
* основные операции выполняются;
* журналы не содержат необработанных ошибок.

**Требование 2. Моделирование остановки контейнера и повторный запуск.**

Искусственно остановить один из контейнеров, участвующих в работе приложения, где, например, можно остановить сервер или другой самостоятельный сервис, остановка которого позволяет наблюдать поведение системы.

Остановка контейнера не обязательно приводит к остановке остальных контейнеров. Поведение зависит от архитектуры приложения и взаимосвязей между компонентами.

После моделирования остановки необходимо запустить контейнер повторно, если контейнер завершился с ошибкой или был удален, может потребоваться другой способ восстановления, например, пересоздание сервиса через Docker Compose.

После запуска необходимо проверить:

* перешел ли контейнер в состояние работы;
* восстановилось ли подключение к сервису;
* выполняются ли основные операции;
* сохранились ли данные;
* появились ли ошибки при восстановлении взаимодействия.

При использовании БД или тома Docker, необходимо отдельно проверить соответствующее хранилище.

**Требование 3. Проверка журналов.**

Изучить журналы контейнеров до остановки, во время отказа и после повторного запуска, где определить:

* какие сообщения появились при запуске;
* как приложение отреагировало на остановку;
* какие ошибки возникли;
* как происходило восстановление;
* удалось ли продолжить работу.

Если в приложении ведется собственный журнал, следует сопоставить его с журналами Docker.

**Требование 4. Сравнение запуска с Docker и без Docker.**

Сравнить два способа запуска одного и того же приложения:

1. Обычный запуск из среды разработки или командной строки.
2. Запуск через Docker и Docker Compose.

Сравнить:

* последовательность запуска;
* необходимые настройки;
* зависимости от установленного окружения;
* способ передачи конфигурации;
* организацию сетевого взаимодействия;
* удобство повторного запуска;
* диагностику ошибок;
* особенности хранения данных.

**Требование 5. Unit и нагрузочное тестирование.**

Дополнить проект тестами, подтверждающими работоспособность приложения после контейнеризации.

Минимально необходимо предусмотреть:

* корректность выполнения основных операций предметной области;
* корректную обработку запроса сервером;
* корректную обработку ошибки при недоступности необходимого компонента;
* корректную обработку невалидного запроса;
* восстановление выполнения операций после повторного запуска сервиса;
* сохранность данных при перезапуске.

Unit-тесты должны проверять логику приложения, а не только факт запуска контейнера.

Дополнительно выполнить **интеграционные тесты** с использованием контейнеризированных компонентов.

Обязательно провести **нагрузочное тестирование**.

**Требование 6. Обработка ошибок.**

Приложение должно корректно обрабатывать следующие ситуации:

* Docker-образ не удалось собрать;
* контейнер не удалось запустить;
* сервер недоступен;
* необходимый сервис недоступен;
* подключение к базе данных завершилось ошибкой;
* сетевое взаимодействие между контейнерами не работает;
* указаны неправильные параметры конфигурации;
* необходимый порт недоступен или занят;
* приложение получило некорректный запрос;
* контейнер остановился во время выполнения операции;
* после повторного запуска сервис временно недоступен;
* данные отсутствуют или недоступны после перезапуска;
* Docker Compose не удалось запустить из-за ошибки конфигурации.

Если необходимый сервис недоступен, приложение должно возвращать понятное сообщение об ошибке.

**Требование 7. Программные требования.**

Сервер должен:

* сохранять функциональность предыдущих ЛР;
* запускаться в Docker-контейнере;
* принимать запросы клиентов;
* использовать необходимые параметры конфигурации;
* взаимодействовать с требуемыми сервисами;
* вести журнал выполнения операций;
* корректно обрабатывать ожидаемые ошибки;
* не зависеть от localhost для обращения к другому контейнеру;
* корректно реагировать на недоступность необходимых компонентов.

Клиент должен:

* подключаться к серверу;
* выполнять операции предметной области;
* отображать результаты операций;
* отображать сообщения об ошибках;
* позволять проверить работу приложения до и после контейнеризации.

Клиент допускается запускать на хосте или в отдельном контейнере.

Docker-конфигурация должна:

* содержать Dockerfile для собственного серверного приложения;
* обеспечивать сборку Docker-образа;
* позволять запускать контейнер;
* содержать compose.yaml для необходимых сервисов;
* обеспечивать сетевое взаимодействие контейнеров;
* использовать переменные окружения для соответствующих настроек;
* позволять остановить и повторно запустить сервисы;
* обеспечивать сохранение данных.
