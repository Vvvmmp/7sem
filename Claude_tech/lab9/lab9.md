**Теоретические сведения**

В предыдущей ЛР приложение было упаковано в Docker-образ и запущено в контейнере. Однако по мере усложнения приложения могут возникнуть дополнительные задачи:

* запуск нескольких экземпляров одного сервиса;
* поддержание заданного количества экземпляров;
* организация стабильного доступа к приложению;
* восстановление экземпляров после некоторых сбоев;
* централизованное описание конфигурации;
* управление большим количеством контейнеризированных компонентов.

Kubernetes предназначен для управления развертыванием и работой контейнеризированных приложений.

**Kubernetes** – платформа оркестрации контейнеризированных приложений, которая позволяет описывать желаемое состояние системы и поддерживать его в пределах возможностей кластера.

Например, разработчик может указать, что серверное приложение должно работать в трех экземплярах. Kubernetes создает необходимые Pod и контролирует их количество, если один из управляемых Pod будет удален, контроллер Deployment обнаружит отклонение от заданного состояния и попытается восстановить требуемое количество экземпляров.

Docker и Kubernetes решают связанные, но разные задачи:

|  |  |
| --- | --- |
| **Технология** | **Основное назначение** |
| Docker | Создание образов и запуск контейнеров |
| Dockerfile | Описание процесса сборки Docker-образа |
| Docker Compose | Совместное описание и локальный запуск нескольких контейнеризированных сервисов |
| Kubernetes | Управление развертыванием, экземплярами и состоянием контейнеризированных приложений |
| kubectl | Взаимодействие с Kubernetes-кластером из командной строки |

**Cluster** – кластер Kubernetes, то есть среда, в которой размещаются и управляются приложения.

Кластер включает управляющие компоненты и узлы, на которых могут выполняться рабочие нагрузки. В учебном примере большая часть инфраструктуры скрыта за инструментами Docker Desktop или Minikube.

Для выполнения ЛР не требуется самостоятельно устанавливать все внутренние компоненты Kubernetes, необходимо уметь проверять доступность кластера и получать информацию о его состоянии.

Основные команды:

* kubectl cluster-info – показывает информацию о кластере;
* kubectl get nodes – показывает список узлов.

**Node** – узел Kubernetes, на котором могут выполняться рабочие нагрузки.

В реальном кластере узлы могут находиться на разных физических или виртуальных машинах, а в локальной конфигурации кластер часто представлен одним узлом.

Необходимо различать количество узлов и количество экземпляров приложения, например, на одном узле могут работать три Pod серверного приложения, при этом команда для просмотра узлов:

kubectl get nodes

Команда для получения подробной информации:

kubectl describe node <имя-узла>

**Pod** – минимальная единица развертывания в Kubernetes.

Pod содержит один или несколько тесно связанных контейнеров, которые совместно используют некоторые ресурсы выполнения. В ЛР один Pod будет содержать один контейнер серверного C# приложения. Pod получает собственный сетевой адрес внутри кластера, этот адрес не рассматривается как постоянный адрес приложения, так как при пересоздании Pod его адрес может измениться. Для просмотра Pod используется команда:

kubectl get pods

Для просмотра подробной информации:

kubectl describe pod <имя-pod>

Возможные состояния и признаки:

* Pending – Pod еще не запущен, например, Kubernetes ожидает доступности необходимых ресурсов;
* Running – Pod привязан к узлу, а его контейнеры созданы, это не всегда означает, что приложение полностью готово обрабатывать запросы;
* Succeeded – выполнение завершилось успешно, что характерно прежде всего для задач, рассчитанных на завершение;
* Failed – выполнение завершилось неуспешно;
* CrashLoopBackOff – контейнер неоднократно завершался, и Kubernetes увеличивает интервалы между попытками его перезапуска;
* Unknown – неизвестное состояние.

Для диагностики состояния необходимо анализировать не только название статуса, но и события, журналы и причину завершения контейнера.

**Deployment** – ресурс Kubernetes, который описывает желаемое состояние развертывания приложения и управляет соответствующими ReplicaSet и Pod.

В Deployment можно указать:

* имя приложения;
* Docker-образ;
* количество экземпляров;
* метки Pod;
* параметры запуска контейнера;
* используемые порты;
* переменные окружения;
* правила обновления развертывания.

Например, параметр replicas: 3 задает желаемое количество трех экземпляров Pod для соответствующего Deployment и если один из управляемых Pod удалить, Deployment через связанные контроллеры обнаружит отклонение от желаемого состояния и попытается создать замену. Deployment не означает, что все экземпляры обязательно будут успешно работать при любых обстоятельствах, восстановление зависит от доступности узлов, ресурсов, образов и корректности конфигурации.

В данной ЛР под экземпляром приложения понимается отдельный Pod, управляемый Deployment.

**Scaling** – изменение количества экземпляров приложения.

Количество экземпляров можно изменить командой:

kubectl scale deployment riot-server --replicas=3

riot-server – это пример имени Deployment. После изменения количества экземпляров можно проверить состояние:

kubectl get deployments

kubectl get pods

Масштабирование не означает автоматическое ускорения любого приложения – результат зависит от характера нагрузки, ресурсов узла, архитектуры сервера, состояния общих данных и доступности зависимых компонентов. Если несколько экземпляров одновременно изменяют общие данные, приложение должно обеспечивать корректность операций. Само увеличение количества Pod не заменяет механизмы синхронизации, транзакций и согласованности данных.

**Service** – ресурс Kubernetes, который предоставляет стабильную точку доступа к группе Pod.

Так как Pod могут пересоздаваться и получать новые сетевые адреса, то неудобно подключаться к каждому Pod по отдельности, но Service позволяет обращаться к выбранным Pod через единый логический адрес и порт. Service использует метки для определения Pod, к которым следует направлять трафик.

В ЛР необходимо настроить Service для доступа к серверному приложению, основные понятия:

* port – порт, на котором доступен Service;
* targetPort – порт контейнера, на который направляется трафик;
* selector – набор меток, по которым Service выбирает Pod;
* type – тип Service, определяющий способ предоставления доступа.

Для ЛР можно использовать Service типа ClusterIP вместе с командой kubectl port-forward – это позволяет обращаться к приложению через локальный порт компьютера без обязательной публикации сервиса наружу.

Для просмотра Service используется команда:

kubectl get services

Service не исправляет ошибки самого приложения и не гарантирует доступность внешней БД, он предоставляет сетевой механизм доступа к подходящим Pod.

**Label** – метка, представляющая собой пару «ключ-значение», которую можно назначить объекту Kubernetes, например:

labels:

app: riot-server

**Selector** – правило выбора объектов по меткам.

Deployment использует метки для управления своими Pod, а Service – для определения Pod, которым следует направлять запросы. Метки в Deployment и селектор Service должны соответствовать друг другу, если Service ищет Pod с меткой app: riot-server, а Pod имеет только метку app: server, Service не сможет выбрать такие Pod по этому селектору – это одна из причин, по которым приложение может быть запущено, но недоступно через Service.

**YAML** – текстовый формат представления структурированных данных.

В Kubernetes YAML применяется для описания ресурсов и их параметров. Пример начала описания Deployment:

apiVersion: apps/v1

kind: Deployment

metadata:

name: riot-server

Поля:

* apiVersion – версия API, к которому относится ресурс;
* kind – тип ресурса;
* metadata – имя и другие метаданные;
* spec – описание желаемого состояния ресурса.

Kubernetes принимает описание ресурса и стремится привести фактическое состояние к указанному, например, в YAML можно задать три экземпляра приложения. После применения конфигурации Kubernetes будет поддерживать заданное количество управляемых Pod, если условия кластера позволяют это сделать.

Для применения конфигурации используется команда:

kubectl apply -f deployment.yaml

Если файл содержит описание существующего ресурса, команда может обновить его конфигурацию.

**ConfigMap** – ресурс Kubernetes для хранения неконфиденциальных параметров конфигурации, например, через ConfigMap можно передавать приложению:

* режим работы;
* название учебной среды;
* параметр поведения;
* адрес или имя используемого сервиса, если это соответствует архитектуре приложения.

Параметры ConfigMap можно передавать контейнеру через переменные окружения.

**Переменная окружения** – параметр, доступный процессу приложения во время выполнения, например, можно определить переменную:

APP\_MODE=kubernetes

Чтобы приложение использовало параметр, в коде C# необходимо прочитать переменную окружения и применить ее значение, например:

string mode =

Environment.GetEnvironmentVariable("APP\_MODE")

?? "default";

default – значение, используемое, если переменная не задана.

В ЛР достаточно создать ConfigMap с одним параметром и показать, что приложение получает его значение. ConfigMap предназначен для неконфиденциальных настроек, пароли и другие секретные данные не следует помещать в ConfigMap или открыто записывать в общедоступный репозиторий.

**kubectl** – инструмент командной строки для взаимодействия с Kubernetes-кластером.

В ЛР используются следующие команды:

|  |  |
| --- | --- |
| **Команда** | **Назначение** |
| kubectl cluster-info | Получение информации о кластере |
| kubectl get nodes | Просмотр узлов |
| kubectl get pods | Просмотр Pod |
| kubectl get deployments | Просмотр Deployment |
| kubectl get services | Просмотр Service |
| kubectl apply -f <файл.yaml> | Применение конфигурации |
| kubectl describe pod <имя> | Подробная информация о Pod |
| kubectl logs <имя-pod> | Просмотр журнала контейнера |
| kubectl scale deployment <имя> --replicas=3 | Изменение количества экземпляров |
| kubectl delete pod <имя> | Удаление Pod для эксперимента |
| kubectl port-forward service/<имя> 8080:8080 | Перенаправление локального порта на Service |
| kubectl delete -f <файл.yaml> | Удаление ресурсов, описанных в файле |

Для просмотра последних событий кластера:

kubectl get events --sort-by=.metadata.creationTimestamp

Для просмотра журналов конкретного Pod необходимо сначала узнать его фактическое имя с помощью kubectl get pods.

При диагностике необходимо последовательно проверить:

1. Доступен ли кластер.
2. Создан ли Deployment.
3. Созданы ли Pod.
4. В каком состоянии находятся Pod.
5. Успешно ли запускается приложение.
6. Совпадают ли метки Pod и селектор Service.
7. Совпадают ли port и targetPort с реальной конфигурацией.
8. Получает ли приложение необходимые параметры.
9. Нет ли ошибок в журналах и событиях Kubernetes.

Kubernetes позволяет описывать желаемое состояние приложения. Контроллеры отслеживают состояние управляемых ресурсов и при определенных условиях предпринимают действия для его восстановления. В ЛР это демонстрируется удалением одного из Pod, управляемых Deployment. После удаления Kubernetes должен попытаться восстановить заданное количество экземпляров, при этом следует различать:

* удаление Pod и завершение процесса приложения;
* перезапуск контейнера внутри Pod;
* пересоздание Pod;
* восстановление доступности приложения;
* восстановление данных;
* восстановление внешних сервисов.

Эти события не являются равнозначными, например, Kubernetes может создать новый Pod, но приложение все равно не сможет выполнять операции, если недоступна БД, если данные хранились только внутри удаленного Pod, Kubernetes не гарантирует их восстановление.

В рамках ЛР необходимо проверить восстановление количества Pod и работоспособность приложения после удаления экземпляра.

В ЛР используется локальный кластер, который может работать на одном компьютере, поэтому необходимо учитывать:

* несколько Pod могут выполняться на одном физическом компьютере;
* отказ компьютера может привести к недоступности всего локального кластера;
* несколько экземпляров приложения не гарантируют независимость от общей БД;
* локальное масштабирование не всегда повышает производительность;
* доступность приложения зависит от корректности его конфигурации и состояния зависимых компонентов.

docker images

Найдите образ серверного приложения и запишите его имя и тег, например, riot-server:1.0.

Для работы Kubernetes должен иметь возможность получить нужный образ – в локальной среде способ зависит от используемого инструмента:

* в Docker Desktop образ может быть доступен локальному Kubernetes при соответствующей конфигурации;
* в Minikube локальный образ при необходимости можно загрузить командой:

minikube image load riot-server:1.0

После этого убедиться, что образ доступен выбранному кластеру:

imagePullPolicy: IfNotPresent

Это позволяет Kubernetes использовать локальный образ, если он уже доступен на узле. Данная настройка не загружает образ автоматически с компьютера пользователя – образ должен быть доступен среде Kubernetes.

**Требование 4. Создание Deployment.**

В каталоге проекта создайте файл deployment.yaml, пример:

apiVersion: apps/v1

kind: Deployment

metadata:

name: riot-server

spec:

replicas: 1

selector:

matchLabels:

app: riot-server

template:

metadata:

labels:

app: riot-server

spec:

containers:

- name: server

image: riot-server:1.0

imagePullPolicy: IfNotPresent

ports:

- containerPort: 8080

Основные параметры:

* kind: Deployment – создаваемый ресурс;
* metadata.name – имя Deployment;
* replicas: 1 – желаемое количество экземпляров;
* matchLabels – метки, по которым Deployment определяет управляемые Pod;
* template.metadata.labels – метки, назначаемые создаваемым Pod;
* image – используемый Docker-образ;
* containerPort – документируемый порт контейнера, используемый приложением, поле containerPort само по себе не изменяет настройки приложения и не публикует порт на компьютере пользователя.

**Требование 5. Применение конфигурации.**

Выполните команду:

kubectl apply -f deployment.yaml

Затем проверьте состояние Deployment и Pod:

kubectl get deployments

kubectl get pods

Если Pod еще не перешел в ожидаемое состояние, получите подробную информацию:

kubectl describe pod <имя-pod>

Для просмотра журнала:

kubectl logs <имя-pod>

Необходимо определить:

* создан ли Deployment;
* создан ли Pod;
* какой Docker-образ используется;
* в каком состоянии находится Pod;
* запустилось ли приложение;
* появились ли сообщения об ошибках.

Если приложение завершилось с ошибкой, необходимо изучить журналы и события, а затем устранить причину.

**Часть 2. Организация доступа к приложению**

**Требование 1. Создание Service.**

Deployment управляет развертыванием приложения, но для организации стабильного доступа к группе Pod необходимо создать Service (service.yaml):

apiVersion: v1

kind: Service

metadata:

name: riot-server

spec:

type: ClusterIP

selector:

app: riot-server

ports:

- port: 8080

targetPort: 8080

protocol: TCP

Назначение параметров:

* kind: Service – создаваемый ресурс;
* type: ClusterIP – Service, доступный внутри кластера;
* selector – метки Pod, к которым направляется трафик;
* port – порт Service;
* targetPort – порт приложения внутри контейнера;
* protocol: TCP – используемый сетевой протокол.

Примените файл:

kubectl apply -f service.yaml

и проверьте созданный Service:

kubectl get services

kubectl describe service riot-server

Необходимо убедиться, что селектор Service соответствует меткам Pod.

**Требование 2. Организация доступа с локального компьютера.**

Для ЛР можно использовать:

kubectl port-forward service/riot-server 8080:8080

Команда перенаправляет соединения с локального порта 8080 на порт Service 8080. Пока команда работает, клиент, запущенный на том же компьютере, может обращаться к серверу через локальный адрес и порт, например, localhost:8080, если используемый клиент и сервер действительно работают с таким протоколом и портом. Команду port-forward обычно нужно оставить работающей в отдельном терминале на протяжении эксперимента, после ее завершения перенаправление прекращается. localhost в данном случае используется клиентом на компьютере пользователя, это не означает, что сервер внутри контейнера должен использовать localhost для обращения к другому Pod.

**Требование 3. Проверка взаимодействия клиента и сервера.**

Запустите клиент и выполните не менее трех операций предметной области, например:

* получение данных;
* создание или изменение записи;
* выполнение операции с общим ресурсом;
* обработка события;
* изменение состояния объекта предметной области.

Для каждой операции необходимо проверить:

1. Клиент отправляет запрос.
2. Сервер получает запрос.
3. Сервер выполняет соответствующую операцию.
4. Клиент получает ожидаемый результат.
5. В журналах нет необработанных ошибок.

Если запрос не проходит, необходимо проверить состояние Pod, Service, порты и журналы приложения.

**Часть 4. Конфигурация, диагностика
и итоговое тестирование**

**Требование 1. Подготовка параметра конфигурации.**

Необходимо подготовить один неконфиденциальных параметров приложения, который можно передавать извне, например:

APP\_MODE=kubernetes

Параметр должен иметь понятное назначение, приложение должно прочитать его и использовать значение в своей работе или журнале, чтение параметра на C#:

string mode =

Environment.GetEnvironmentVariable("APP\_MODE")

?? "default";

Console.WriteLine($"Application mode: {mode}");

Пример демонстрирует получение настройки и вывод ее значения, если приложение использует собственную систему конфигурации, допускается встроить параметр в нее.

**Требование 2. Создание ConfigMap.**

Создайте файл configmap.yaml, например:

apiVersion: v1

kind: ConfigMap

metadata:

name: riot-config

data:

APP\_MODE: "kubernetes"

Примените конфигурацию:

kubectl apply -f configmap.yaml

Затем измените deployment.yaml, чтобы передавать значение ConfigMap приложению, пример фрагмента конфигурации контейнера:

env:

- name: APP\_MODE

valueFrom:

configMapKeyRef:

name: riot-config

key: APP\_MODE

Этот фрагмент необходимо добавить внутрь описания контейнера в Deployment, он заменяет или дополняет соответствующий раздел env, если такой раздел уже существует. После изменения примените конфигурацию:

kubectl apply -f deployment.yaml

Проверьте состояние Pod и журнал приложения:

kubectl get pods

kubectl logs <имя-pod>

Необходимо убедиться, что приложение получило параметр и использовало его, если изменяется значение ConfigMap, необходимо учитывать, что переменная окружения уже запущенного процесса автоматически не меняется, чтобы новое значение попало в окружение контейнера, может потребоваться пересоздание Pod, например, через обновление Deployment или его перезапуск.

Необходимо намеренно создать одну ошибку конфигурации, определить ее причину и исправить. Рекомендуемый вариант – временно указать в deployment.yaml неправильное имя Docker-образа или тег, который недоступен выбранному кластеру, например, заменить:

**Требование 6. Unit-тестирование.**

* обработки невалидного запроса;
* обработки ожидаемой ошибки;
* корректности используемого параметра конфигурации, если для него реализована логика.

Unit-тесты из предыдущих лабораторных работ необходимо использовать и дополнить их при необходимости.

**Требование 7. Обработка ошибок.**

Необходимо уметь диагностировать следующие ситуации:

* Kubernetes-кластер недоступен;
* kubectl обращается не к тому контексту;
* Docker-образ отсутствует в среде Kubernetes;
* указан неправильный тег образа;
* Pod не запускается;
* приложение завершается с ошибкой;
* Service не выбирает необходимые Pod;
* неправильно указаны port или targetPort;
* локальное перенаправление порта не работает;
* приложение не получает параметр ConfigMap;
* имя ConfigMap или ключ указаны неправильно;
* после изменения конфигурации приложение продолжает использовать прежнее значение;
* после удаления Pod новый экземпляр не запускается;
* приложение недоступно из-за ошибки зависимого компонента.

При обнаружении ошибки необходимо:

1. Зафиксировать наблюдаемое состояние.
2. Получить подробную информацию о соответствующем ресурсе.
3. Просмотреть события и журналы.
4. Определить вероятную причину.
5. Исправить конфигурацию.
6. Повторно проверить состояние и выполнить запрос.

Не следует считать приложение работоспособным только потому, что команда kubectl apply завершилась успешно, эта команда подтверждает применение конфигурации, но не гарантирует, что приложение успешно запустилось и обрабатывает запросы.

**Требование 9. Программные требования.**

Сервер должен:

* сохранять функциональность предыдущих лабораторных работ;
* запускаться в Docker-контейнере, развернутом в Kubernetes;
* принимать запросы клиентов;
* выполнять операции предметной области;
* использовать необходимые параметры конфигурации;
* вести журнал выполнения операций;
* корректно обрабатывать ожидаемые ошибки;
* не зависеть от localhost для обращения к другому контейнеру или сервису;
* корректно реагировать на недоступность необходимых компонентов.

Клиент должен:

* подключаться к серверу;
* выполнять операции предметной области;
* отображать результаты операций;
* отображать сообщения об ошибках;
* позволять проверить работу приложения до и после развертывания в Kubernetes.

Клиент допускается запускать на компьютере пользователя, в этом случае необходимо обеспечить доступ к серверу с помощью подходящего способа, например, kubectl port-forward.

Конфигурация Kubernetes должна:

* содержать Deployment для серверного приложения;
* использовать правильный Docker-образ;
* задавать количество экземпляров;
* содержать Service для организации доступа;
* обеспечивать соответствие селектора Service меткам Pod;
* позволять изменять количество экземпляров;
* позволять проверить восстановление после удаления Pod;
* содержать ConfigMap с неконфиденциальным параметром;
* передавать параметр приложению;
* позволять диагностировать и исправлять ошибки конфигурации.
