**Теоретические сведения**

В процессе разработки ПО разработчики регулярно изменяют исходный код, добавляют новые функции, исправляют ошибки и объединяют свои изменения с общей версией проекта и, если каждое изменение необходимо вручную собирать, тестировать, упаковывать и развертывать, то процесс становится медленным и может сопровождаться ошибками, например, разработчик может:

* изменить исходный код;
* забыть выполнить сборку проекта;
* не заметить ошибку в одном из модулей;
* создать Docker-образ из неправильной версии приложения;
* развернуть приложение, которое не прошло тестирование.

Чтобы уменьшить количество подобных проблем, используются практики CI/CD.

**CI/CD (Continuous Integration/Continuous Delivery/Continuous Deployment)** – совокупность практик автоматизации разработки, проверки, сборки и доставки программного обеспечения.

CI/CD позволяет организовать последовательный процесс, в котором изменения исходного кода автоматически проходят необходимые проверки и подготавливаются к развертыванию.

**Continuous Integration (непрерывная интеграция)** – практика регулярного объединения изменений исходного кода с общей версией проекта и автоматической проверки результата.

При использовании CI разработчик отправляет изменения в Git-репозиторий, после этого система автоматизации получает актуальный исходный код, восстанавливает зависимости, выполняет сборку и запускает тесты, при этом последовательность CI:

1. Разработчик изменяет исходный код.
2. Создает commit.
3. Отправляет изменения в Git-репозиторий.
4. Система автоматизации получает новую версию кода.
5. Выполняется восстановление зависимостей.
6. Выполняется сборка проекта.
7. Запускаются автоматические тесты.
8. Формируется результат проверки.

Если сборка или тестирование завершаются ошибкой, разработчик получает информацию о проблеме и может исправить ее до дальнейшей доставки приложения.

После проверки исходного кода нужно подготовить приложение к использованию, и для этого применяются две связанные практики.

**Continuous Delivery (непрерывная доставка)** – практика автоматической подготовки проверенной версии приложения к развертыванию.

После успешной сборки и тестирования приложение упаковывается в готовый артефакт, например, Docker-образ, его можно использовать для развертывания в тестовой или производственной среде. Само развертывание может запускаться после дополнительного подтверждения.

**Continuous Deployment (непрерывное развертывание)** – практика, при которой успешно прошедшие все проверки изменения автоматически развертываются в целевой среде без отдельного ручного подтверждения.

В ЛР необходимо настроить автоматическую цепочку, в которой после успешной сборки и тестирования создается Docker-образ и выполняется развертывание приложения в Kubernetes, то есть практическая реализация будет демонстрировать CI и автоматизированное развертывание, соответствующее подходу Continuous Deployment.

**Pipeline (конвейер)** – последовательность автоматизированных этапов, которые выполняются для обработки изменений исходного кода, где каждый этап отвечает за определенную операцию.

В ЛР №10 используется следующая последовательность:

|  |  |
| --- | --- |
| **Этап** | **Назначение** |
| Checkout | Получение исходного кода из Git |
| Restore | Восстановление зависимостей .NET |
| Build | Сборка проекта |
| Test | Запуск автоматических тестов |
| Package | Создание Docker-образа |
| Deploy | Развертывание новой версии в Kubernetes |

Переход к следующему этапу должен происходить только после успешного выполнения предыдущего обязательного этапа, например, если Unit-тесты завершились ошибкой, Pipeline не должен переходить к созданию Docker-образа и развертыванию новой версии. Это позволяет не доставлять в целевую среду версию приложения, которая не прошла необходимые проверки.

**Jenkins** – сервер автоматизации, предназначенный для выполнения задач, связанных со сборкой, тестированием и доставкой программного обеспечения, он позволяет создавать задания, которые выполняются вручную или автоматически при наступлении определенных событий.

С помощью Jenkins можно:

* получать исходный код из Git;
* запускать команды сборки;
* выполнять автоматические тесты;
* создавать Docker-образы;
* взаимодействовать с Kubernetes;
* сохранять результаты выполнения заданий;
* отображать ошибки и журналы;
* запускать последовательности действий в виде Pipeline.

В ЛР Jenkins будет центральным компонентом автоматизации, то есть разработчик не должен вручную выполнять все команды после каждого изменения исходного кода, а вместо этого он отправляет изменения в Git, а Jenkins выполняет настроенную последовательность действий.

**Jenkins Job** – задание, которое Jenkins выполняет по заданным правилам.

**Jenkins Pipeline** – описание последовательности этапов выполнения задания.

Для ЛР используется Pipeline, существует несколько способов определить его последовательность:

* создать Pipeline непосредственно в интерфейсе Jenkins;
* хранить описание Pipeline в файле Jenkinsfile внутри Git-репозитория.

В ЛР №10 работе необходимо использовать второй способ.

**Jenkinsfile** – текстовый файл, содержащий описание Pipeline, он хранится вместе с исходным кодом проекта и позволяет версионировать процесс автоматизации.

Пример структуры Jenkinsfile (одного этапа):

pipeline {

agent any

stages {

stage('Test') {

steps {

// Запуск тестов

}

}

}

}

Здесь:

* pipeline – начало описания Pipeline;
* agent any – Jenkins может использовать доступный исполнитель;
* stages – набор этапов;
* stage – отдельный этап;
* steps – команды, выполняемые на этапе.

Внутри этапов размещаются команды, которые должны выполняться в определенной последовательности.

Git используется для хранения исходного кода приложения и управления изменениями. Jenkins может получать исходный код непосредственно из Git-репозитория.

В ЛР используется следующий сценарий:

1. Изменяется C#-проект.
2. Сохраняются изменения.
3. Создается commit.
4. Отправляются изменения в Git-репозиторий.
5. Jenkins получает актуальную версию проекта.
6. Запускается Pipeline.

Для получения изменений Jenkins может использовать несколько способов запуска задания:

* ручной запуск;
* периодическую проверку Git-репозитория (по расписанию);
* Webhook – уведомление от Git-сервиса о новом изменении.

В рамках ЛР допускается использовать ручной запуск или периодическую проверку репозитория.

**Poll SCM** – механизм периодической проверки репозитория на наличие новых изменений, если Jenkins обнаруживает изменения, он запускает соответствующее задание.

При использовании GitHub Webhook GitHub может отправлять Jenkins уведомление сразу после отправки нового commit.

Для сборки приложения используется .NET SDK, где основные команды:

|  |  |
| --- | --- |
| **Команда** | **Назначение** |
| dotnet restore | Восстановление зависимостей проекта |
| dotnet build | Сборка проекта |
| dotnet test | Запуск автоматических тестов |
| dotnet publish | Подготовка приложения к публикации |

В ЛР Jenkins должен автоматически выполнить восстановление зависимостей, сборку и тестирование, например:

dotnet restore

dotnet build --configuration Release

dotnet test --configuration Release

Если проект состоит из нескольких частей, необходимо учитывать его структуру.

**Unit Testing (модульное тестирование)** – проверка отдельных элементов программного обеспечения, например, методов и классов. В CI/CD Unit-тесты позволяют автоматически проверять корректность логики приложения после получения новых изменений.

Jenkins анализирует результат выполнения команды, если команда завершилась с ошибкой, Pipeline получает статус Failed и прекращает выполнение последующих этапов, если для них не настроено специальное поведение. Таким образом, ошибка тестирования должна препятствовать созданию и развертыванию новой версии приложения.

После успешной сборки и тестирования приложение необходимо упаковать в Docker-образ.

Для сборки образа используется команда:

docker build -t riot-server:1.0 .

В ЛР допускается использовать номер сборки Jenkins в качестве тега Docker-образа.

В ЛР №9 создали Deployment и Service, запустили приложение в Kubernetes и проверили его работу. В данной работе необходимо автоматизировать развертывание новой версии приложения, после успешного выполнения сборки, тестирования и создания Docker-образа Jenkins должен выполнить команду обновления образа в Kubernetes, например:

kubectl set image deployment/riot-server server=riot-server:15

Здесь:

* deployment/riot-server – имя Deployment;
* server – имя контейнера внутри Deployment;
* riot-server:15 – новый Docker-образ.

Для проверки результата используется команда:

kubectl rollout status deployment/riot-server

Она позволяет дождаться завершения обновления Deployment и получить информацию о результате.

После развертывания необходимо проверить состояние ресурсов:

kubectl get deployments

kubectl get pods

Также необходимо выполнить контрольный запрос к приложению через Service и убедиться, что новая версия работает. В рамках ЛР допускается использовать локальную конфигурацию, в которой Jenkins и Kubernetes имеют доступ к одному Docker-образу. Необходимо учитывать, что создание образа на компьютере пользователя само по себе не означает, что этот образ автоматически доступен Kubernetes.

Одна из главных задач CI/CD – не только автоматизировать успешный процесс, но и предотвращать доставку некорректных версий приложения.

В ЛР необходимо проверить несколько ситуаций:

|  |  |
| --- | --- |
| **Ситуация** | **Ожидаемое поведение** |
| Проект успешно собирается | Pipeline переходит к тестированию |
| Сборка завершается ошибкой | Pipeline останавливается |
| Unit-тесты завершаются ошибкой | Pipeline не переходит к созданию Docker-образа |
| Docker-образ успешно создан | Pipeline может перейти к развертыванию |
| Развертывание завершилось ошибкой | Pipeline получает статус Failed |
| Все этапы завершились успешно | Pipeline получает статус Success |

Для моделирования ошибки необходимо временно изменить тест так, чтобы он завершался неуспешно. После эксперимента необходимо восстановить правильную реализацию теста, и повторно запустить Pipeline.

**Требование 4. Создание Jenkinsfile.**

В корне Git-репозитория создайте файл Jenkinsfile. На первом этапе необходимо подготовить простую структуру Pipeline, содержащую этап Checkout, например:

pipeline {

agent any

stages {

stage('Checkout') {

steps {

checkout scm

}

}

}

}

Здесь checkout scm позволяет получить исходный код из репозитория, указанного в настройках задания Jenkins, добавьте Jenkinsfile в Git, после этого откройте задание в Jenkins, выполните первый запуск и проверьте:

* успешно ли Jenkins получил исходный код;
* какая ветка используется;
* какой commit был получен;
* нет ли ошибок доступа к репозиторию;
* завершился ли Pipeline успешно.

Если задание не может получить исходный код, необходимо проверить URL репозитория, выбранную ветку и учетные данные.

**Часть 2. Настройка Continuous Integration**

**Требование 1. Определение структуры проекта.**

Перед настройкой сборки необходимо определить, какие проекты должны собираться и тестироваться, если в проекте используется файл решения .sln, допускается выполнять команды для всего решения.

Определить:

* путь к серверному проекту;
* путь к тестовому проекту;
* используемую версию .NET;
* способ запуска нагрузочных, интеграционных и Unit-тестов;
* расположение файлов проекта в Git-репозитории.

Все дальнейшие команды должны соответствовать структуре проекта.

**Требование 2. Добавление этапа Restore.**

В Jenkinsfile необходимо добавить этап восстановления зависимостей:

stage('Restore') {

steps {

bat 'dotnet restore Server/Server.csproj'

bat 'dotnet restore Tests/Tests.csproj'

}

}

Если используется решение .sln, нужно выполнить восстановление зависимостей для него.

Назначение этапа:

* получение необходимых пакетов;
* подготовка проекта к сборке;
* проверка возможности восстановления зависимостей.

После добавления этапа сохраните Jenkinsfile и отправьте изменения в Git, запустите Pipeline и проверьте результат.

**Требование 3. Добавление этапа Build.**

После восстановления зависимостей добавить этап сборки:

stage('Build') {

steps {

bat 'dotnet build Server/Server.csproj --configuration Release --no-restore'

}

}

Если проект использует решение .sln, допускается выполнять сборку всего решения.

Параметр --configuration Release задает конфигурацию сборки Release. --no-restore указывает, что восстановление зависимостей уже было выполнено на предыдущем этапе.

После запуска Pipeline необходимо проверить:

* успешно ли выполнена сборка;
* отсутствуют ли ошибки компиляции;
* какие предупреждения появились;
* сформированы ли результаты сборки.

Если сборка завершается ошибкой, необходимо изучить Console Output и исправить проблему в исходном коде или конфигурации проекта.

**Требование 4. Добавление этапа Test.**

После успешной сборки необходимо добавить этап тестирования (самостоятельно). В результате Jenkins должен автоматически запускать нагрузочные, интеграционные и Unit-тесты, необходимо проверить:

* запускаются ли все предусмотренные тесты;
* сколько тестов выполнено;
* сколько тестов завершилось успешно;
* есть ли неуспешные тесты;
* отображается ли результат выполнения в Console Output.

При необходимости можно использовать вывод тестов в формате TRX:

dotnet test Tests/Tests.csproj --configuration Release --logger "trx"

Этот формат позволяет сохранять результаты тестирования в виде отдельного файла.

**Требование 5. Итоговый Jenkinsfile для CI и проверка автоматического получения изменений.**

После добавления этапов Checkout, Restore, Build и Test Jenkinsfile должен содержать последовательность определенной структуры.

После изменения Jenkinsfile:

1. Сохраните файл.
2. Выполните commit.
3. Отправьте изменения в Git.
4. Запустите Pipeline.
5. Проверьте последовательность этапов.

Убедиться, что Jenkins получает актуальный исходный код, а для этого:

1. Откройте один из файлов проекта.
2. Внесите небольшое корректное изменение.
3. Сохраните файл.
4. Создайте commit.
5. Отправьте изменения в Git.
6. Запустите Pipeline повторно.

В качестве дополнительной настройки использовать Poll SCM, чтобы Jenkins периодически проверял Git-репозиторий на наличие изменений, где в настройках задания можно указать расписание проверки, например:

H/2 \* \* \* \*

Это пример периодической проверки примерно раз в две минуты, но фактическое время запуска определяется планировщиком Jenkins.

**Требование 6. Моделирование ошибки тестирования.**

Проверить, как Jenkins реагирует на неуспешный тест. Для этого временно измените один из тестов таким образом, чтобы он завершался неуспешно, например, можно изменить ожидаемое значение в Assert.

После этого:

1. Сохраните изменение.
2. Создайте commit.
3. Отправьте изменения в Git.
4. Запустите Pipeline.
5. Дождитесь выполнения этапа Test.
6. Проверьте общий статус Pipeline.

Ожидаемый результат:

* Checkout выполняется успешно;
* Restore выполняется успешно;
* Build выполняется успешно;
* Test завершается ошибкой;
* Pipeline получает статус Failed;
* Package и Deploy не выполняются.

После завершения эксперимента обязательно восстановите правильную реализацию теста, нужно отправить исправление в Git и убедиться, что Pipeline снова выполняется успешно.

**Часть 3. Автоматизация создания Docker-образа**

**Требование 1. Подготовка Dockerfile.**

Для создания Docker-образа необходимо использовать Dockerfile, подготовленный в ЛР №8, проверьте:

* находится ли Dockerfile в Git-репозитории;
* правильно ли указан путь к проекту;
* соответствует ли Dockerfile структуре текущего проекта;
* успешно ли образ создается вручную;
* запускается ли созданный контейнер.

Если Dockerfile находится в корне репозитория, в качестве контекста сборки можно использовать текущий каталог.

**Требование 2. Проверка доступа Jenkins к Docker.**

Убедитесь, что Jenkins может выполнять Docker-команды, где нужно проверить доступность Docker:

docker --version

docker info

Команды должны выполняться из того же окружения, в котором работает Jenkins, если Jenkins не может обращаться к Docker, проверить:

* установлен ли Docker;
* запущен ли Docker Engine;
* доступен ли Docker в PATH;
* имеет ли учетная запись Jenkins необходимые права;
* доступен ли Docker Engine для процесса Jenkins.

Если Jenkins работает как служба Windows, может потребоваться настройка прав и перезапуск службы после изменения конфигурации.

**Требование 3. Добавление этапа Package.**

В Jenkinsfile необходимо добавить этап создания Docker-образа, в качестве тега образа использовать номер сборки Jenkins, пример:

stage('Package') {

steps {

bat 'docker build -t riot-server:%BUILD\_NUMBER% .'

}

}

В примере:

* docker build запускает сборку образа;
* riot-server – имя образа;
* %BUILD\_NUMBER% – номер текущей сборки Jenkins;
* . – текущий каталог как контекст сборки.

**Требование 4. Проверка создания образа.**

После добавления этапа Package:

1. Сохраните Jenkinsfile.
2. Отправьте изменения в Git.
3. Запустите Pipeline.
4. Дождитесь успешного выполнения этапов Checkout, Restore, Build и Test.
5. Проверьте выполнение этапа Package.

После завершения Pipeline выполните:

docker images

Найдите созданный образ, а для получения подробной информации можно использовать:

docker image inspect riot-server:15

Проверьте:

* существует ли Docker-образ;
* правильно ли указано имя;
* соответствует ли тег номеру сборки;
* завершилась ли сборка образа без ошибок.

**Требование 5. Проверка зависимости Package от Test.**

Убедиться, что Docker-образ создается только после успешного тестирования, а для этого повторите эксперимент из части 2.

Если Jenkins остановил Pipeline после ошибки тестирования, поведение соответствует требованию ЛР. После эксперимента восстановите правильный тест и отправьте исправления в Git.

**Часть 4. Автоматизация развертывания в Kubernetes
и итоговое тестирование**

**Требование 1. Подготовка Kubernetes.**

В данной части необходимо использовать локальный кластер Kubernetes, подготовленный в ЛР №9.

Проверьте доступность кластера:

kubectl cluster-info

kubectl get nodes

Проверьте существование Deployment:

kubectl get deployments

Проверьте наличие Pod:

kubectl get pods

Необходимо убедиться, что:

* кластер запущен;
* Jenkins может обращаться к Kubernetes;
* существует Deployment серверного приложения;
* имя Deployment известно;
* имя контейнера внутри Deployment известно;
* приложение доступно через Service.

Проверьте, какой Docker-образ используется в текущем Deployment, для этого можно выполнить:

kubectl describe deployment riot-server

**Требование 2. Проверка доступа Jenkins к Kubernetes.**

Команды Kubernetes должны выполняться из окружения Jenkins, проверьте:

kubectl get deployments

kubectl get pods

Если команды выполняются успешно, Jenkins имеет доступ к выбранному Kubernetes-кластеру, если команды завершаются ошибкой, необходимо проверить:

* установлен ли kubectl;
* доступен ли kubectl в PATH;
* какой Kubernetes-контекст используется;
* существует ли необходимая конфигурация подключения;
* имеет ли учетная запись Jenkins права на выполнение операций.

При запуске Jenkins от отдельной учетной записи Kubernetes может не использовать тот же файл kubeconfig, что и пользователь, который вручную выполняет команды в терминале, тогда необходимо организовать доступ Jenkins к нужному кластеру и предоставить минимально необходимые права. Не следует размещать пароли, токены и другие секретные данные непосредственно в Jenkinsfile или открытом Git-репозитории.

**Требование 3. Доступность Docker-образа для Kubernetes.**

Перед развертыванием необходимо убедиться, что Kubernetes может получить образ, созданный Jenkins.

Вариант 1. Docker Desktop.

Если Jenkins и локальный Kubernetes используют один Docker Engine и общую среду образов, созданный образ может быть доступен Kubernetes непосредственно. Необходимо проверить, что образ доступен кластеру.

Вариант 2. Minikube.

Если используется Minikube, то локальный образ может потребоваться загрузить в среду Minikube:

minikube image load riot-server:15

В ЛР допускается выполнять передачу образа в Minikube непосредственно на этапе Deploy. Наличие образа в выводе команды docker images не гарантирует, что Kubernetes сможет его использовать, необходимо учитывать, в какой среде фактически работает кластер.

**Требование 4. Добавление этапа Deploy и итоговый Jenkinsfile.**

После успешного выполнения этапа Package необходимо добавить в Jenkinsfile этап развертывания (самостоятельно).

В результате Jenkins должен:

1. Получить исходный код.
2. Выполнить восстановление зависимостей.
3. Собрать проект.
4. Запустить нагрузочные, интеграционные и Unit-тесты.
5. Создать Docker-образ.
6. Обеспечить доступность образа для Kubernetes.
7. Обновить Deployment.
8. Дождаться завершения обновления.

После добавления всех этапов Jenkinsfile должен содержать последовательность. Pipeline выполняет автоматическое развертывание после успешного тестирования, поэтому перед запуском убедитесь, что Jenkins работает с нужным кластером и обновляет именно тот Deployment, который используется в ЛР.

**Требование 5. Проверка результата развертывания.**

После успешного выполнения Pipeline необходимо проверить состояние Kubernetes и используемый образ. Необходимо убедиться, что:

* Deployment существует;
* обновление завершилось;
* Pod находится в состоянии Running;
* используется новый Docker-образ;
* количество доступных экземпляров соответствует настройкам Deployment.

Проверьте доступность приложения через Service, если в ЛР №9 использовался port-forward, можно повторно выполнить:

kubectl port-forward service/riot-server 8080:8080

После этого запустите клиент и проверьте основные операции предметной области.

**Требование 6. Проверка автоматического обновления приложения.**

Необходимо продемонстрировать, что новое изменение исходного кода приводит к автоматическому созданию и развертыванию новой версии приложения, для этого:

1. Откройте исходный код серверного приложения.
2. Внесите небольшое корректное изменение, которое можно проверить во время работы приложения.
3. Сохраните изменения.
4. Создайте commit.
5. Отправьте изменения в Git.
6. Запустите Pipeline.
7. Дождитесь успешного выполнения всех этапов.
8. Проверьте новый Docker-образ.
9. Проверьте обновление Deployment.
10. Выполните контрольный запрос к приложению.

Например, можно изменить текст информационного сообщения, которое сервер выводит при запуске, или добавить небольшое изменение в доступную операцию предметной области. Необходимо убедиться, что новая версия действительно была собрана и развернута, а не просто повторно запущена старая версия.

**Требование 7. Проверка обработки ошибок.**

Необходимо повторно проверить поведение Pipeline при возникновении ошибок. Минимально необходимо продемонстрировать два варианта.

Вариант 1. Ошибка тестирования.

* изменить один тест так, чтобы он завершался ошибкой;
* отправить изменения в Git;
* запустить Pipeline;
* убедиться, что этапы Package и Deploy не выполняются.

Вариант 2. Ошибка развертывания.

* временно указать неправильное имя Deployment или контейнера в этапе Deploy;
* запустить Pipeline с корректно проходящими тестами;
* проверить, что этап Deploy завершается ошибкой;
* определить причину ошибки по Console Output;
* восстановить правильное имя;
* повторно запустить Pipeline.

После эксперимента обязательно восстановите корректную конфигурацию и убедитесь, что Pipeline завершается успешно.

**Требование 8. Итоговое тестирование.**

После настройки Pipeline необходимо выполнить итоговую проверку, где минимально требуется:

* убедиться, что Jenkins получает актуальный исходный код из Git;
* проверить успешное выполнение Restore;
* проверить успешную сборку проекта;
* проверить выполнение всех тестов;
* убедиться, что Docker-образ создается автоматически;
* проверить имя и тег образа;
* убедиться, что Kubernetes использует новую версию образа;
* проверить состояние Deployment и Pod;
* проверить доступность приложения через Service;
* выполнить не менее трех операций предметной области;
* проверить журналы приложения;
* убедиться, что Pipeline останавливается при ошибке тестирования;
* восстановить корректную версию проекта после эксперимента;
* выполнить Pipeline повторно и получить успешный результат.

**Требование 9. Программные требования.**

Сервер должен:

* сохранять функциональность предыдущих ЛР;
* собираться с использованием .NET SDK;
* содержать операции предметной области;
* корректно обрабатывать ожидаемые ошибки;
* иметь автоматические тесты;
* сохранять совместимость с Dockerfile из ЛР №8;
* запускаться в Kubernetes;
* вести журнал выполнения основных операций.

Клиент должен:

* подключаться к серверу;
* выполнять операции предметной области;
* отображать результаты операций;
* отображать сообщения об ошибках;
* позволять проверить работу приложения после автоматизированного развертывания.

Git-репозиторий должен:

* содержать исходный код проекта;
* содержать исходный код тестов;
* содержать Dockerfile;
* содержать Jenkinsfile;
* содержать необходимые конфигурационные файлы;
* не содержать открытых паролей, токенов и других секретных данных.

Jenkins Pipeline должен:

* получать исходный код из Git;
* восстанавливать зависимости;
* собирать проект;
* запускать тесты;
* создавать Docker-образ после успешных проверок;
* использовать уникальный тег Docker-образа;
* выполнять развертывание в Kubernetes;
* проверять результат обновления Deployment;
* прекращать выполнение последующих этапов при ошибке обязательного этапа;
* отображать результат выполнения и сообщения об ошибках.

Конфигурация Kubernetes должна:

* содержать Deployment серверного приложения;
* использовать правильный Docker-образ;
* содержать Service для организации доступа;
* позволять проверить состояние Pod;
* позволять обновлять используемый Docker-образ;
* обеспечивать доступность приложения после успешного развертывания.
