**Теоретические сведения**

В предыдущих ЛР компоненты приложения работали по схеме:

Client → Server → Database

или сервер напрямую обращался к другим компонентам:

![](data:image/png;base64...)

Такая схема работает, но сервер должен знать о каждом компоненте. Если необходимо добавить новый компонент, например, AnalyticsService, сервер придется изменить, при этом количество связей между компонентами увеличивается. Модель Pub/Sub позволяет изменить эту схему.

**Publish/Subscribe (Pub/Sub)** – это модель взаимодействия, в которой один компонент публикует событие, а другие компоненты подписываются на интересующие их события, где общая схема:

![](data:image/png;base64...)

Publisher не должен напрямую обращаться к каждому Subscriber, он сообщает Broker, что произошло событие такого типа, а Broker определяет, какие подписчики заинтересованы в этом событии, и передает его им.

**Event** – сообщение, описывающее произошедшее событие. Например, для интернет-магазина после создания заказа может возникнуть OrderCreated. Событие может содержать:

EventType = OrderCreated

OrderId = 125

ClientId = 7

Timestamp = 10:15:32

Событие описывает факт произошедшего действия, а не обязательно является командой для выполнения этого действия.

**Publisher** – компонент, который публикует события, например:

![](data:image/png;base64...)

Publisher передает событие Broker и онне должен напрямую обращаться к Subscriber.

**Broker** – компонент, который принимает опубликованные события и доставляет их подписчикам, где схема может выглядеть так:

![](data:image/png;base64...)

Broker должен:

* принимать события;
* хранить информацию о подписках;
* определять подходящих подписчиков;
* передавать им события;
* фиксировать ошибки доставки;
* продолжать работу при отказе отдельного Subscriber.

**Subscriber** – компонент, который подписывается на определенные типы событий, например:

Logger:

OrderCreated

OrderCancelled

StockService:

OrderCreated

NotificationService:

OrderCreated

OrderCancelled

То есть один Subscriber может получать только интересующие его события.

В ЛР №6 в качестве простого варианта можно использовать **тип события** как идентификатор подписки, например: OrderCreated, OrderCancelled, PaymentCompleted. Подписчик может зарегистрировать:

Subscribe("OrderCreated")

Broker после этого знает:

![](data:image/png;base64...)

**Прямое взаимодействие:**

![](data:image/png;base64...)

Сервер знает о каждом компоненте.

**Pub/Sub:**

![](data:image/png;base64...)

Publisher не знает конкретный состав подписчиков. Это позволяет уменьшить связанность компонентов.

Одно из основных преимуществ Pub/Sub – **слабая связанность (Loose coupling)**.

Publisher знает, что ему нужно опубликовать событие OrderCreated, но Publisher не обязан знать:

* сколько подписчиков существует;
* какие именно компоненты получают событие;
* где они расположены;
* как они обрабатывают событие.

Это особенно полезно в распределенных системах, где компоненты могут изменяться независимо.

Одно событие может быть передано нескольким подписчикам:

![](data:image/png;base64...)

Все три компонента получают одно событие, но выполняют разные действия.

В распределенной системе Subscriber может обрабатывать событие независимо от Publisher, что позволяет отделить публикацию события от его дальнейшей обработки.

В ЛР допускается использовать Task и искусственные задержки для демонстрации независимой обработки.

**Требование 5. Обработка ошибок.**

Приложение должно корректно обрабатывать следующие ситуации:

* сервер недоступен;
* Broker недоступен;
* Publisher не может опубликовать событие;
* Subscriber недоступен;
* ошибка соединения с Subscriber;
* Subscriber не зарегистрирован;
* отсутствует подписка на указанный тип события;

* ошибка обработки события;

Если один Subscriber недоступен, приложение не должно аварийно завершаться, а остальные Subscriber должны продолжать обработку события. Если Broker недоступен, Publisher должен получить понятный результат ошибки, а сервер не должен аварийно завершаться.
